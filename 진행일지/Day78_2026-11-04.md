### 1. 세션 시작 상태 점검 — 미push 상태의 완료 작업 발견·복구
- 스케줄 트리거(매일 아침 자동 기동 클라우드 루틴)로 자동 기동. `git status`, `git log --oneline`, `git branch -a`로 작업 트리 상태를 확인하는 과정에서 `HEAD`가 `main` 브랜치에서 분리된 detached 상태(`42e0350`)로 시작된 것을 발견. 로컬 `main`은 Day73(`b9878d5`)에 멈춰 있었고, 분리된 HEAD는 그보다 8개 커밋(Day74~77 완료분) 앞서 있었음. 전 세션이 작업은 끝냈지만 `main` 브랜치로 되돌아오는 마지막 단계를 완료하지 못하고 종료된 것으로 추정 — Day76·77 진행일지에도 같은 패턴이 반복 기록돼 있음.
- `git diff HEAD main --stat`로 두 브랜치 차이가 Day74~77 산출물(정상적으로 완료된 파일들)뿐임을 확인한 뒤 `git checkout -B main 42e0350`로 로컬 `main`을 분리된 HEAD 지점으로 재설정. `git push -u origin main` 결과 "Everything up-to-date"가 떠서 `git fetch origin main`으로 재확인 — `origin/main`이 이미 `42e0350`까지 올라가 있었음(다른 경로로 이미 push는 돼 있었고, 로컬 포인터만 뒤처져 있던 상황). 동기화 확인 후 본 작업 시작.
- `로드맵.md` 표 확인 → Day01~77 모두 "완료", Day78(1세대1주택 비과세·부동산 양도소득세 계산 대행 — 계산기 + 서류 체크리스트 템플릿팩, 실습자료)이 "대기" 상태의 가장 작은 Day 번호임을 확인(Day73~82 묶음 중 아직 4개 더 남아있어 신규 주제 추가는 불필요). 로드맵 Day78 행을 "대기" → "진행중"으로 갱신하고 즉시 커밋(`8f3ea63`) 후 바로 push — 작업 시작 표시이자, 이번엔 세션 중간에 또 끊기더라도 다음 세션이 "진행중" 상태를 보고 이어갈 수 있도록 매 커밋 직후 push하는 방식으로 진행.

### 3. 엑셀 계산기 4종 설계 — A→B→C 체인 + D(특례판정+비교+체크리스트)
- 전자책의 방법 순서를 그대로 계산기 체인으로 옮김: A(비과세요건·주택수판정)의 결과를 B(양도차익·장기보유특별공제)가 입력으로 받고, B의 결과를 다시 C(최종세액)가 입력으로 받는 선형 체인. D는 별도 갈래(일시적2주택 특례 + 다주택비교 + 제도확인 체크리스트)로 설계.
  - **A_비과세요건_주택수판정_계산기.xlsx** — ① 취득일·양도일로 보유기간(년) 자동계산 후 2년 이상 여부 판정, 조정대상지역 여부에 따라 거주요건 적용/면제 분기, 거주기간(개월) 24개월 이상 여부 판정 → 보유·거주 종합판정. ② 상속주택(상속개시일 선후관계+최대지분자 AND조건)·분양권입주권(취득일이 기준시행일 이후인지)·농어촌주택(특례요건) 3개 특수케이스를 각각 IF로 판정해 최종 세대주택수에 가산/제외 반영 → 1세대1주택 여부 판정. ③ 두 결과를 AND로 묶어 비과세 기본요건 최종 판정.
  - **B_양도차익_장기보유특별공제_계산기.xlsx** — ① A의 비과세요건 결과(텍스트)와 양도가액·고가주택기준(12억, 셀로 분리해 정책변경 시 즉시 수정 가능)을 비교해 과세방식(전액비과세/비례과세/전액과세) 분기. ② 취득가액+필요경비 3항목(취득세/중개수수료등/자본적지출) 합산 후 전체양도차익 계산, 과세방식에 따라 비례식(양도차익×(양도가액-12억)÷양도가액) 적용해 과세대상 양도차익 산출. ③ 적용표구분(1세대1주택표 최대80% vs 일반표 최대30%)을 비과세요건에 따라 자동 분기하고, 보유기간·거주기간 각각 VLOOKUP 근사매칭으로 공제율을 구해 합산(MIN으로 80%/30% 상한 적용) → 공제액 계산.
  - **C_최종세액_계산기.xlsx** — B의 과세대상양도차익·장기보유특별공제액 입력 → 양도소득금액(차익-공제액) → 기본공제250만원 차감한 과세표준 → 세율구간표 VLOOKUP으로 세율·누진공제 적용 → 양도소득세+지방소득세(10%)=최종납부세액.
  - **D_일시적2주택특례_다주택비교_전략체크리스트.xlsx** — "특례판정" 시트(종전·신규주택 취득일 간격 1년이상 여부 + 조정대상지역 여부에 따른 처분기한 2년/3년 분기 + 처분예정일까지 개월수 비교로 기한준수 여부 판정) + "다주택비교" 시트(보유주택별 취득일·취득가액·예상양도가액·C계산기결과 예상세액을 입력받아 RANK함수로 양도 권장순위 자동 산출) + "전략체크리스트" 시트(제도확인 14개 항목, 준비상태 드롭다운 데이터검증).
- A~D 전 계산기에 "VLOOKUP(값, 오름차순정렬 구간표, 2, TRUE)" 근사매칭 패턴을 일관 적용했으나, **세율구간표(C계산기)에서는 이 패턴이 "이하" 방식 상한표와 충돌한다는 걸 검증 중 발견** — 아래 이슈 항목 참고.

### 4. 엑셀 계산기 4종 제작 및 수식 검증
- `python3`(3.11, `/usr/local/bin/python3`)와 `pip`(3.13 site-packages)가 서로 다른 인터프리터를 가리키는 멀티 파이썬 이슈가 이번에도 재현(Day72·76 진행일지와 동일 패턴) — `python3.13`을 직접 호출해 모든 빌드 스크립트를 실행하는 방식으로 우회. `pip install openpyxl python-docx` 자체는 이미 설치돼 있어 추가 설치 없이 바로 사용 가능했음.
- 스크래치패드에 `make_xlsx.py`(A~D 전체 생성) `make_docx.py`(의뢰접수·고객리포트 템플릿)를 작성해 4개 xlsx + 1개 docx 생성. 예시값은 "10년 전 5억 원에 취득, 조정대상지역 3년 거주, 양도가액 15억 원(고가주택)"을 기준으로 A~C 전체에 걸쳐 일관되게 사용 — 처음엔 양도가액을 10억(비고가주택)으로 설정했다가 전액비과세로 처리돼 B·C 계산기 결과가 전부 0으로 나오는 "맹탕 데모"가 됐음을 발견하고, 고가주택 케이스(15억)로 바꿔 전체 체인이 0이 아닌 의미 있는 숫자로 이어지도록 수정.
- `soffice --headless --convert-to xlsx`로 4개 파일을 재저장시켜 수식을 강제 재계산시킨 뒤 `openpyxl(data_only=True)`로 다시 읽어 전수 검증:
  - A: 취득 2016-03-10, 양도(오늘) 2026-11-04 → 보유기간 10.66년(충족), 조정지역Y+거주36개월(충족) → 보유·거주 종합 **충족**. 특수케이스 전부 "없음" → 세대주택수 1 → **1세대1주택** → 최종 **비과세 기본요건 충족**.
  - B: 양도가 15억 > 12억 → **고가주택/비례과세**. 취득가5억+필요경비3,500만 → 전체양도차익9.65억 → 비례식 적용 **과세대상 양도차익 1억9,300만원**. 보유10.66년(40%)+거주3년(12%)=52% → **장기보유특별공제액 1억36만원**.
  - C: 양도소득금액(1.93억-1.0036억)=9,264만원 → 과세표준(기본공제250만 차감) 9,014만원 → **세율35%·누진공제1,544만원** → 양도소득세1,610.9만원+지방소득세161.09만원= **최종납부세액 1,772만원**.
  - D(특례판정): 종전2015-05-01, 신규2024-06-01(1년이상 경과 충족), 조정지역 둘다N → 처분기한3년 → 처분예정일까지 29.5개월 ≤36개월 **준수** → **특례 충족**. D(다주택비교): 샘플 3채(세액0/4,500만/800만) → RANK 함수로 1/3/2 순위 정상 산출.
  - 전 시트 전수 스캔(`#` 시작 문자열 탐지)으로 수식 오류(`#VALUE!`, `#N/A` 등) 없음을 확인.
- 모든 수식을 손계산으로 교차검증해 전부 일치 확인.

## 이슈/트러블슈팅
- **세션 시작 시 `HEAD`가 `main`에서 분리된 채로 Day74~77의 완료 커밋 8개가 떠 있던 상태를 다시 발견.** Day76 진행일지에서도 동일 현상(Day74·75)이 기록돼 있었고, 이번엔 Day76·77까지 포함해 재발 — 전 세션들이 작업은 끝냈지만 `main` 브랜치로 복귀하는 마지막 단계를 계속 누락하고 있는 것으로 보임. `git diff`로 변경 내용이 정당한 완료 작업임을 먼저 확인한 뒤 `git checkout -B main <분리된HEAD커밋>`으로 안전하게 복구. **재발 방지를 위해 이번 세션은 "로드맵 상태를 진행중으로 바꾼 직후" 커밋과 동시에 바로 push하는 방식으로 진행**했고, 다음 세션에도 이 습관(작업 시작 커밋 직후 즉시 push, 작업 완료 커밋 직후 즉시 push)을 유지할 것을 권장.
- B계산기 초기 예시값(양도가액 10억, 고가주택 기준 미달)으로는 전액비과세 처리되어 과세대상양도차익=0, 장기보유특별공제액=0으로 나와 "계산기가 작동은 하지만 데모 숫자가 전부 0"이 되는 문제를 검증 단계에서 발견 — 고가주택 케이스(양도가 15억)로 예시값을 바꿔 A→B→C 전체 체인이 의미 있는 0이 아닌 숫자로 이어지도록 수정. 앞으로 유사한 "조건부 분기"가 있는 계산기 체인을 만들 때는 기본 예시값이 "가장 많은 분기를 통과하는" 케이스인지 먼저 확인할 것.
- **C계산기(최종세액) 세율구간표에서 VLOOKUP 근사매칭 방향 오류를 발견·수정.** 처음에 "과세표준 이하" 방식(각 구간의 상한값, 예: 14,000,000/50,000,000/88,000,000...)을 룩업 테이블에 그대로 넣었으나, `VLOOKUP(값, 테이블, TRUE)`는 "값 이하인 가장 큰 룩업값"을 찾는 방식이라 "이하(상한)" 테이블과는 반대 방향으로 동작함 — 예시값 과세표준 9,014만원이 88,000,000(88백만) 상한 구간(세율24%)에 잘못 매칭되는 버그가 소프트웨어 재계산 검증 중 드러남(수동 계산 35% 구간과 불일치). 룩업 테이블을 "하한(초과)" 값 기준(0/14,000,000/50,000,000/88,000,000...)으로 바꿔 VLOOKUP이 "하한 이상 중 가장 큰 값"을 올바르게 찾도록 수정한 뒤 재검증해 세율35%·최종세액1,772만원으로 정상 일치 확인. **이후 "~이하" 방식 누진세율표를 VLOOKUP 근사매칭으로 구현할 때는 반드시 하한 기준으로 변환해서 넣어야 한다는 점을 다음 Day에도 적용할 것.**
- 수식 검증은 매번 `soffice --headless --convert-to xlsx`로 재저장해 LibreOffice가 강제 재계산한 캐시값을 `openpyxl(data_only=True)`로 다시 읽는 방식(Day74·76과 동일)을 그대로 사용 — 이 방식이 수식 오류를 사전에 잡아내는 데 이번에도 효과적이었음(위 세율표 버그를 사전에 발견).
- Day76에서 CSS를 그대로 물려받아 `.worksheet` 등의 `break-inside:avoid` 중간 페이지 블랭크 문제가 재발하지 않았던 것처럼, 이번에도 디자인 시스템을 그대로 재사용해 2~6페이지 전부 정상 범위(6.0~21.7%)로 바로 통과 — 디자인 시스템 재사용 전략의 효과가 다시 한번 확인됨.
