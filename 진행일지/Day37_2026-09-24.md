### 5. PDF 렌더링 및 페이지 여백 검증 — 페이지 수 판정에서 시행착오
- `scripts/render_pdf_cloud.js`로 렌더링 → 실제 페이지 수를 poppler(`pdfinfo`/`pdftoppm` 미설치) 없이 확인하기 위해 PDF 원본 바이트에서 `/Type /Page` 패턴을 정규식으로 세었더니 14가 나왔는데, 이는 오탐이었음(문서 내 다른 객체가 패턴에 우연히 매칭). `scripts/screenshot_pdf_pages_cloud.js`(Chrome 내장 뷰어를 PageDown으로 스크롤하며 캡처)로 14장을 캡처해서 Read로 열어보니 툴바에 "N / 14"로 표시되어 14페이지가 맞는 것으로 보였으나, 캡처된 이미지들의 실제 페이지 번호를 다시 대조하니 일부 구간(9→11, 9→13 등)에서 페이지가 건너뛰어 중복/누락이 있었음(Day36 진행일지에서 이미 기록된 "뷰포트가 페이지보다 살짝 커서 PageDown이 페이지 경계를 넘어간다"는 동일 현상).
- 해결: `#page=N&zoom=page-fit` 앵커로 Playwright가 직접 특정 페이지로 이동해 캡처하는 방식(`page.goto('file:///.../day37.pdf#page=N&zoom=page-fit')`)으로 전환해 1~14페이지를 빠짐없이 개별 확인. 실제 페이지 수는 툴바 표시대로 **14페이지**였음(PDF 내부의 `/Count 8`은 최상위가 아닌 중첩된 Pages 노드의 부분 카운트였던 것으로 추정, 이 수치는 신뢰하지 않기로 함).
- 14페이지 전체를 육안 확인한 결과: 표지(1p)는 독립 페이지로 정상, 본문 카드(표·프롬프트 그리드·체크리스트)가 페이지 경계에서 자연스럽게 이어지며 중간에 30% 이상 비는 페이지 없음. 마지막 14p는 에필로그 클로징 문구만 있어 하단 여백이 있으나, 이는 Day35/36과 동일한 책 말미 통상 여백 패턴이라 문제로 보지 않음.

## 이슈/트러블슈팅
- **poppler(`pdftoppm`/`pdfinfo`) 미설치 환경에서 PDF 페이지 수를 정규식으로 추정하면 안 됨** — `/Type /Page` 카운트도, PDF 내부 `/Count` 필드도 중첩된 Pages 트리 구조 때문에 오탐/부분값이 나올 수 있음(이번엔 14가 정답, `/Count 8`은 오답이었음). **가장 신뢰할 수 있는 방법은 Chrome 내장 PDF 뷰어를 열어 툴바의 "N / 총페이지" 표시를 직접 확인하는 것.**
- **`scripts/screenshot_pdf_pages_cloud.js`의 PageDown 스크롤 캡처가 이번에도 페이지를 건너뜀** (Day36에서 이미 보고된 동일 현상, 뷰포트가 A4 페이지보다 살짝 커서 발생). 이번 세션에서 대안으로 `page.goto('file:///경로.pdf#page=N&zoom=page-fit')` 앵커 방식(페이지 번호를 직접 지정해서 이동)을 사용해 모든 페이지를 정확히 개별 캡처했음 — **다음 세션부터는 페이지 여백 검증 시 처음부터 이 방식을 쓸 것을 권장** (PageDown 스크롤 방식은 짧은 문서든 긴 문서든 신뢰도가 낮음이 Day36·Day37 두 세션 연속 확인됨).
- 위 두 트러블슈팅 모두 이번 세션에서 해결까지 완료했고 최종 PDF 14페이지 전체를 육안으로 확인해 여백 문제가 없음을 확인했다.
