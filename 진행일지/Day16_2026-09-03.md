# Day 16 — 2026-09-03

## 목표

## 진행 과정

### 1. 저장소 상태 점검
- 세션 시작 시 로컬 HEAD가 detached 상태(`c0d32ed`, Day15 마지막 커밋)였음. `git fetch origin main`으로 원격을 확인했더니 로컬 HEAD와 `origin/main`이 이미 일치 — 밀린 커밋 없음. `git checkout -B main origin/main`으로 정상 `main` 브랜치로 전환(Day14 일지에서 예상했던 대로 이번에도 detached HEAD로 시작 — 클라우드 세션이 매번 새 컨테이너에서 시작하는 구조상 계속 재발하는 패턴으로 확인됨).
- `로드맵.md`를 읽고 Day16("AI로 데이터 분석 리포트 자동화 — 실전 템플릿 + 예시 리포트", 실습자료, 대기)이 가장 위 대기 항목임을 확인.
- Day16 행 상태를 `대기` → `진행중`으로 갱신 후 단독 커밋(`Day16 작업 시작: ...`), 푸시 성공 확인.

### 3. 콘텐츠 설계
- 전자책의 "방법 1(리포트 유형별 템플릿)"과 "방법 7(업종별 맞춤)"을 워크시트 2·3으로, "방법 9(검증)"를 워크시트 4로, "방법 10(패키지·가격)"을 워크시트 5로, 신규로 "리포트 브리프 접수 양식"(워크시트 1)을 추가해 총 5개 워크시트로 구성.
- 체크리스트는 전자책의 12가지 방법을 시간 순서가 아니라 **리포트 한 건이 처리되는 실무 프로세스 4단계**(접수&데이터 정제 → 지표 추출&시각화 설계 → 인사이트 작성&검증 → 납품&정기구독 전환)로 재구조화 — Day14와 동일한 "프로세스 단계형" 패턴을 재사용(이 상품도 "고객 1건당 반복되는 워크플로우"이므로).
- 프롬프트는 전자책의 16개를 A 데이터 정제·구조화(8)/B 지표·인사이트 추출(8)/C 리포트 작성·시각화(8)/D 업종별 맞춤(8)/E 운영·가격·확장(8) 5개 카테고리 총 40개로 확장 — Day14 일지에 남긴 교훈("카테고리별 프롬프트 개수를 모두 짝수로 맞춰 2열 그리드 마지막 줄 단독 카드 방지")을 그대로 적용해 전 카테고리를 8개씩 균등 배분.
- **표준 리포트 템플릿**(`templates/리포트_표준_템플릿.md`)은 표지→한줄요약(헤드라인)→핵심지표(KPI)→시각화→인사이트(숫자+원인추정+근거 3단 구조)→액션아이템→검증메모→다음리포트예고 순서로 설계, 전자책 방법 1~9의 순서를 그대로 문서 구조에 반영.
- **예시 리포트**(`templates/예시_리포트_카페매출.md`)는 가상의 카페 "온기로스터스"(실존 업체 아님을 파일 내 명시)의 8월 매출 데이터로 템플릿을 처음부터 끝까지 채운 견본으로 제작 — 신메뉴 출시로 인한 매출 증가, 화요일 매출 부진이라는 두 축의 인사이트를 "숫자→원인추정→근거"로 서술하고, "검증 메모"에서 8/25 임시공휴일 이상치를 AI가 재검토 지적하는 과정까지 포함시켜 실제 작업 흐름을 보여주도록 구성.
- `templates/업종별_핵심지표_정의표.csv`는 전자책 방법 7의 표(업종군/강조포인트/피해야할표현)에 리포트유형·핵심지표·추천차트·데이터출처예시 열을 추가해 확장.

### 4. 산출물 제작 및 PDF 페이지 여백 버그 발견·수정 (중요)
- `resources/kit.html` 작성 — Day14 kit.html의 CSS(디자인 토큰, `.worksheet`/`.checklist-group`/`.prompt-grid` 클래스 관례)를 그대로 재사용.
- `scripts/render_pdf_cloud.js`로 1차 렌더링(11페이지) 후 `scripts/screenshot_pdf_pages_cloud.js`로 전 페이지 확인하던 중, **2페이지(인트로 챕터)에서 페이지의 약 30%가 빈 채로 남고 "01 워크시트" 섹션 전체가 3페이지로 밀리는 현상**을 발견. Playwright로 각 요소의 `getBoundingClientRect()`를 직접 측정하는 스크립트(`/tmp/measure.js`, 임시)를 작성해 원인을 정확히 규명: `h2.chapter{break-after:avoid-page}`가 헤딩을 바로 다음 워크시트 카드에 강제로 붙이는데, 인트로 섹션이 짧게 끝나 남은 페이지 공간(약 300px)이 워크시트1 카드(약 386px)보다 작아 **헤딩+카드 전체가 통째로 다음 페이지로 밀려나면서** 인트로 페이지 하단이 크게 비는 구조적 문제였음. (동일 패턴이 Day14 kit.html PDF의 2페이지에도 이미 존재했으나 그 날 일지에는 기록되지 않았던 것으로 확인 — 이번에 처음 표면화됨.)
  - **1차 수정**: 인트로 섹션에 실질적으로 유용한 콘텐츠("이런 상황이면 바로 펼치세요" 3단계 사용 시나리오 목록 + "전자책 없이도 이 키트만으로 충분하다"는 안내 노트)를 추가해 인트로가 페이지를 더 채우도록 조정. 재렌더링 후 해당 페이지의 빈 공간이 약 8% 수준으로 감소, 전체 페이지 수가 11 → 10으로 줄어듦.
  - **2차 발견**: 동일 스크립트로 4페이지(워크시트 3·4 이후 워크시트 5가 다음 페이지로 밀리는 지점)에서도 같은 유형의 문제(약 40% 여백)를 추가로 발견 — 워크시트3+4 합산 높이가 남은 공간보다 근소하게(약 20px) 초과해 워크시트5 전체가 밀려남.
  - **2차 수정**: 워크시트3의 안내 노트 문구를 한 줄 분량으로 축약(2줄→1줄, 약 20px 절감)해 워크시트5가 같은 페이지에 들어오도록 조정. 재렌더링 후 5개 워크시트가 3~4페이지에 걸쳐 빈틈없이 배치됨을 확인.
  - **전 페이지(1~10) 육안 재검증**: `single_page.js`(임시 스크립트, PDF를 `#page=N&zoom=page-fit`로 한 페이지씩 정확히 캡처)로 10페이지 전체를 다시 확인. 표지(의도된 여백, 정상), 인트로, 워크시트 1~5, 표준 템플릿·예시 리포트 안내, 체크리스트 1~4단계, 프롬프트팩 A~E(2열 그리드로 정확히 짝을 맞춰 배치), 에필로그(마지막 페이지 하단 여백은 시리즈 관례상 정상)까지 전 페이지에서 30% 이상 빈 공간이 남는 곳이 없음을 확인.
  - 임시 측정 스크립트(`/tmp/measure.js`, `/tmp/single_page.js`)는 저장소 밖(`/tmp`)에 작성해 사용 후 정리했으며, 저장소에는 반영하지 않음(재사용이 필요해지면 `scripts/`에 정식으로 추가하는 것을 고려할 것 — "다음 액션" 참고).
- `.cover` 요소를 673px 뷰포트(A4 실제 인쇄 폭)로 캡처해 표지 문구 확인 — 부제 "표준 리포트 템플릿 + 채워진 예시 리포트, 업종별 워크시트 5개, 그대로 쓰는 프롬프트 40개"가 "업종별"과 "다음날" 두 단어 지점에서 어색하게 줄바꿈되는 것을 발견해 `<span class="nowrap">`으로 감싸 수정, 재캡처로 정상 줄바꿈 확인.
- `resources/templates/리포트_표준_템플릿.md`, `예시_리포트_카페매출.md`, `업종별_핵심지표_정의표.csv`, `README.md` 작성 (3번 항목 참고).

- **PDF 페이지 여백 버그(신규 발견, 이번 Day의 핵심 이슈)**: "인트로 섹션이 짧게 끝나면 다음 챕터의 헤딩+첫 카드 전체가 다음 페이지로 밀리며 이전 페이지 하단이 크게 빈다"는 패턴을, 이번에 처음으로 `getBoundingClientRect()` 기반 정밀 측정으로 원인까지 규명해 수정함(4번 항목 참고). 이 패턴은 Day14 kit.html에도 동일하게 존재하는 것으로 확인됐으나 그날은 육안 검수에서 놓쳤던 것으로 보임 — Day14를 소급 수정하지는 않았으나(이번 실행 범위는 Day16 하나로 한정), **앞으로 다른 Day의 kit.html/ebook.html을 만들 때도 "인트로 챕터 직후"와 "워크시트/체크리스트 묶음 중간"을 최우선으로 육안 검수할 것 — 특히 챕터 헤딩 바로 다음에 오는 첫 카드가 가장 크다면 그 챕터가 새 페이지에서 시작할 가능성이 높으므로, 헤딩 앞 섹션(인트로 등)의 내용량을 여유 있게 채워두는 것이 예방책**임을 이번에 확인함.
- 그 외 렌더링/스크린샷 도구(`render_pdf_cloud.js`, `screenshot_pdf_pages_cloud.js`, `screenshot_element_cloud.js`)는 Day02~15에서 이미 검증된 그대로 문제없이 재사용됨. 특이 오류 없음.
