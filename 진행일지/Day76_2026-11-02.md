### 1. 세션 시작 상태 점검 — 미push 상태의 완료 작업 발견·복구
- 스케줄 트리거(매일 아침 자동 기동 클라우드 루틴)로 자동 기동. `git log --oneline`, `git status`, `git branch -a`로 작업 트리 상태를 확인하는 과정에서 `HEAD`가 `main` 브랜치에서 분리된 detached 상태(`e4bce9a`)로 시작된 것을 발견. 분리된 커밋 4개(`973113c`→`d713660`→`f1e05ca`→`e4bce9a`)를 조사해보니 Day74(연말정산 환급액 계산 템플릿팩, 실습자료)와 Day75(주택청약 가점·당첨 전략 계산 대행, 전자책) 두 Day 분량의 완성된 작업이 로컬 `main` 브랜치에 fast-forward 병합도, `origin/main`에 push도 되지 않은 채 분리된 상태로 남아있었음. 전 세션이 작업은 끝냈지만 `main` 브랜치로 되돌아오거나 push하는 마지막 단계를 완료하지 못하고 종료된 것으로 추정.
- 데이터 유실 위험을 피하기 위해 `git diff main e4bce9a`로 변경 내용 전체(로드맵.md 상태 갱신 2줄 + Day74·75 산출물 18개 파일)를 먼저 검토해 정당한 완료 작업임을 확인한 뒤, `git checkout main && git merge --ff-only e4bce9a`로 fast-forward 병합. `git push -u origin main` 시도 결과 "Everything up-to-date"가 떠서 재확인해보니 `origin/main`이 이미 해당 커밋까지 올라가 있던 상태(다른 경로로 이미 push는 돼 있었고, 로컬 `main` 브랜치 포인터만 뒤처져 있던 상황)였음 — `git fetch origin main`으로 `origin/main == main == e4bce9a` 동기화 확인 후 본 작업 시작.
- `로드맵.md` 표 확인 → Day01~75 모두 "완료", Day76(주택청약 가점·당첨 전략 계산 대행 — 계산기 + 전략 체크리스트 템플릿팩, 실습자료)이 "대기" 상태의 가장 작은 Day 번호임을 확인(Day73~82 묶음 중 아직 7개 더 남아있어 신규 주제 추가는 불필요). 로드맵 Day76 행을 "대기" → "진행중"으로 갱신하고 즉시 커밋(`54c6588`) — 작업 시작 표시.

### 3. 엑셀 계산기 4종 설계 — A/B 독립, C가 A·B 결과를 이어받는 구조
- Day74(연말정산)처럼 전체가 하나의 긴 체인은 아니고, A(무주택기간)·B(부양가족수)는 서로 독립적으로 계산 가능하되 C(가입기간·총점·당첨가능성)가 A·B의 최종 점수만 입력받아 합산하는 구조로 설계:
  - **A_무주택기간_점수계산기.xlsx** — 생년월일·혼인여부·혼인신고일·과거주택 보유·처분이력을 입력하면 ①산정 기준일(30세된날과 혼인신고일 중 빠른 날, 처분이력 있으면 처분일로 재산정)이 자동 확정되고, ②신청일을 입력하면 무주택기간(년)과 점수(VLOOKUP 근사매칭, 0~15년 구간표)가 자동 계산.
  - **B_부양가족수_점수계산기.xlsx** — 세대원 최대 6명의 관계구분·나이·세대등재기간·혼인여부를 입력하면 중첩 IF 수식으로 배우자(무조건 포함)/직계존속(등재3년↑)/직계비속(미혼+30세미만 또는 등재1년↑) 포함 여부를 자동 판정하고, COUNTIF로 집계한 인원수에 VLOOKUP으로 점수(0명~6명이상, 5점~35점)를 매칭.
  - **C_가입기간_총점_당첨가능성계산기.xlsx** — ①청약통장 최초가입일·미성년 가입이력(있다면 성년전환일까지 기간에서 인정한도를 적용)으로 인정 가입기간과 점수(0.5년 단위 세분 구간표, 1점~17점)를 계산 → ②A·B 점수를 노란 칸에 옮겨 입력하면 가입기간 점수와 더해 84점 만점 총점 자동 합산 → ③관심 단지의 과거 당첨 최저·평균 가점을 입력하면 총점과 비교한 당첨 가능성(가능성 있음/경계선/어려움 3단계)을 IF 중첩으로 자동 판정.
  - **D_가점제추첨제비교_전략체크리스트.xlsx** — "D-day계산기+체크리스트" 2시트 패턴을 재사용하되, Day72·74의 날짜 기반 D-day 대신 "가점 상승 시점 계산기"로 성격을 바꿈: ①주택형별 공급세대수·가점제비율을 입력하면 가점제·추첨제 물량(세대수)이 자동 계산되는 표 → ②총점·커트라인 비교로 권장 전략(가점제 물량 신청 / 추첨제 병행) 자동 판정 → ③현재 무주택기간·가입기간을 입력하면 MOD 함수로 다음 정수년(또는 0.5년) 상승까지 남은 기간과 예상일을 자동 계산하는 '가점 상승 시점 계산기'. 두 번째 시트 '전략체크리스트'는 특별공급 5유형(신혼부부·생애최초·다자녀·노부모부양·기관추천)+부부전략 3항목+제도확인 4항목+최종확인 2항목, 총 14개 항목을 구분·항목·확인방법·준비상태(드롭다운: 준비완료/확인중/미착수/해당없음)·비고 컬럼으로 정리.
- VLOOKUP 근사매칭(4번째 인자 TRUE) 패턴을 전 계산기의 배점표 룩업에 일관되게 사용 — 오름차순 정렬된 구간표에서 "입력값 이상인 가장 큰 구간"을 찾는 방식이 전자책의 "N년~N+1년 미만 = M점" 구간 배점표와 정확히 일치함을 확인.

### 4. 엑셀 계산기 4종 제작 및 수식 검증
- `pip3 install openpyxl python-docx` 실행 시 `python3`(3.11, `/usr/local/bin/python3`)와 `pip3`(3.13 site-packages로 설치)가 서로 다른 인터프리터를 가리키는 멀티 파이썬 이슈를 재확인(Day72 진행일지에 남겨둔 메모와 유사한 증상이지만 이번엔 원인이 달랐음 — `python3 -m pip install`이 조용히 아무 동작 안 하고 종료됐었는데, 알고 보니 `pip3 install`은 실제로 3.13에 설치가 됐고 `/usr/local/bin/python3`만 3.11을 가리키고 있던 것). `python3.13`을 직접 호출해 모든 빌드 스크립트를 실행하는 방식으로 우회.
- `openpyxl`로 공통 스타일 함수를 `style_lib.py`에 분리(헤더/입력칸/결과칸/최종강조/참고문구 헬퍼, 드롭다운 헬퍼)한 뒤 A~D 4개 xlsx 파일 생성 스크립트(`build_xlsx.py`, `build_b.py`, `build_c.py`, `build_d.py`, `build_docx.py`)를 `/tmp/.../scratchpad/day76/`에 작성. 예시값은 생년월일 1988-05-14·2019-03-02 혼인·배우자+자녀2명 부양·청약통장 2011-06-10 가입을 기준으로 전 계산기에 일관되게 사용.
- `soffice --headless --convert-to xlsx`로 4개 파일을 재저장시켜 수식을 강제 재계산시킨 뒤 `openpyxl(data_only=True)`로 다시 읽어 전수 검증:
  - A: 생년월일 1988-05-14, 혼인 2019-03-02(기혼) → 30세된날 2018-05-14 = 기준일(혼인신고일보다 빠름, 처분이력 없음) → 신청일(오늘 2026-11-02) 기준 무주택기간 8.48년 → **18점(8년~9년 구간)**
  - B: 배우자(포함)+자녀2명(미혼·9세·6세, 각각 30세미만 조건으로 포함)+부모(세대등재 2년, 3년 미만이라 제외) → 포함 3명 → **20점(3명 구간)**
  - C: 최초가입 2011-06-10, 미성년 이력 없음 → 가입기간 15.41년 → **17점(15년이상 만점)**. 총점 = A입력24(예시)+B입력25(예시)+C연동17 = **66점**. 커트라인62점과 비교 → **"가능성 있음"**
  - D: 59㎡(80세대·가점제70%)→가점제56/추첨제24, 74㎡(120세대·75%)→90/30, 84㎡(150세대·80%)→120/30 — 전부 손계산과 일치. 총점76(예시) vs 커트라인72 → **"가점제 물량으로 신청"**. 가점상승계산기: 현재무주택기간10.4년 입력 시 MOD(10.4,1)=0.4≠0 → 남은기간 0.6년 → 다음상승예상일 **2027-06-09**(오늘+219일) 자동계산 확인, 현재가입기간15.1년(15년이상) → **"만점(17점) 도달"** 판정 정상 작동.
- 모든 수식을 손계산으로 교차검증해 전부 일치 확인 — Day74에서 겪었던 "안내 문구의 셀 좌표 오기재" 같은 실수를 피하기 위해, README·sales_page 작성 전에 먼저 이 검증 결과를 수치 그대로 적어두고 나중에 그 숫자를 그대로 재사용.

## 이슈/트러블슈팅
- **세션 시작 시 `HEAD`가 `main`에서 분리된 채로 Day74·75의 완료 커밋 4개가 떠 있던 상태를 발견.** 전 세션이 작업을 끝내고도 `main` 브랜치로 복귀/병합하는 마지막 단계를 완료하지 못하고 종료된 것으로 추정됨. `git diff`로 변경 내용이 정당한 완료 작업임을 먼저 확인한 뒤 `git merge --ff-only`로 안전하게 병합 — 이후 세션은 작업 시작 전에 항상 `git branch -a`와 `git log --oneline -5` 결과에서 "HEAD detached" 여부를 먼저 확인하는 습관을 들일 것.
- `pip3 install`과 `python3 -m pip install`이 서로 다른 파이썬 인터프리터(3.13 vs 3.11)를 가리키는 멀티 파이썬 이슈가 이번에도 재현됨 — `python3.13`을 직접 호출하는 방식으로 우회(Day72 진행일지의 메모와 현상은 비슷하나 원인은 이번이 다름: 이번엔 설치 자체는 됐으나 실행 인터프리터가 달랐던 경우).
- 시스템 Pillow(`/usr/lib/python3/dist-packages/PIL`)가 `_imaging` 네이티브 확장 모듈 없이 깨진 상태로 설치돼 있어 `scan_page_margins.py` 실행이 즉시 실패 — Day74에서 남긴 해결책(`python3 -m pip install --force-reinstall pillow numpy`)을 그대로 적용해 바로 해결. 매 세션 컨테이너가 새로 시작되는 구조상 이 오류는 계속 재현될 가능성이 높으므로, 다음 Day에서도 동일 오류(`cannot import name '_imaging'`)가 나오면 바로 이 명령으로 해결할 것.
- A~D 계산기 전체에 걸쳐 "N년 이상 ~ (N+1)년 미만 = M점" 구간 배점표를 `VLOOKUP(값, 오름차순정렬구간표, 2, TRUE)` 근사매칭 패턴 하나로 통일해서 구현 — Day74의 "최저사용액 단계적 차감" 수식보다 훨씬 단순하면서도 전자책의 모든 배점표(무주택기간·부양가족수·가입기간)에 동일하게 적용 가능함을 확인. 이후 유사한 "구간별 점수/등급" 계산기를 만들 때 재사용할 수 있는 패턴.
- Day74에서 CSS를 그대로 물려받아 `.worksheet` 등의 `break-inside:avoid` 중간 페이지 블랭크 문제가 재발하지 않았던 것처럼, 이번에도 디자인 시스템을 그대로 재사용해 2~6페이지 전부 정상 범위(8.1~21.7%)로 바로 통과 — 디자인 시스템 재사용 전략의 효과가 반복 확인됨.
