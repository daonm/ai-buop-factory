# Day 06 — 2026-08-24

## 목표
로드맵.md의 대기 항목 중 가장 위(Day 06) — "AI로 상세페이지 카피 잘 쓰는 법 — 업종별 템플릿 + 프롬프트팩" (유형: 실습자료)을 제작한다. Day05 전자책(『사장님, 그 카피로는 안 팔립니다』)과 짝을 이루는 업셀 상품으로, "방법은 읽었는데 내 상품엔 어떻게 적용하지?"라는 다음 질문에 답하는 실행 도구를 만드는 것이 목표.

## 진행 과정

### 2. 기존 산출물 검토
- `products/day02_ai-부수입-가이드-실행키트/resources/kit.html`(실습자료 디자인 기준 예시)와 `products/day05_ai-상세페이지-카피/ebook/ebook.html`(짝이 되는 전자책, 가장 최근 디자인)을 완독해 색상 토큰·폰트·`.worksheet`/`.prompt-grid`/`.checklist-group` 컴포넌트 구조를 확인.
- Day05 전자책의 "방법 8 — 업종별 상세페이지 템플릿 5종"(뷰티/화장품, 식품, 전자기기/가전, 서비스, 디지털 콘텐츠) 표를 이번 실습자료의 뼈대로 그대로 계승하기로 결정 — 원리를 설명한 챕터를 실제로 "표 빈칸만 채우면 되는" 실행 도구로 구체화하는 것이 이 상품의 핵심 가치.
- `진행일지/Day05_2026-08-23.md`를 템플릿 겸 최근 트러블슈팅 이력(특히 `p{ orphans:1; widows:1; }` 권장 사항) 확인용으로 완독.

### 3. 최신 트렌드 조사
- `WebSearch`로 "2026 상세페이지 카피 트렌드 스마트스토어 쿠팡 전환율 높이는 구조" 검색.
- 핵심 발견: (1) 2026년 상세페이지는 **모듈형·짧은 호흡** 구조가 표준 — 모바일 기준 [히어로 컷 → 핵심 혜택 3개 → 구성/옵션 → 사용 시나리오 → 리뷰 → FAQ → CTA] 순서, (2) 초개인화(타겟별 강조점 자동 변경) 트렌드, (3) 스마트스토어 권장 이미지 규격 가로 860px, 쿠팡 가로 780px.
- 이 7모듈 구조를 5개 업종 템플릿 전체의 공통 뼈대로 채택 — Day05 전자책의 "강조 순서"(예: 뷰티=성분→효과→후기→비교)는 이 7모듈 안에서 업종별로 무엇을 강조할지 결정하는 기준으로 통합.

### 4. 콘텐츠 설계 결정
- 구성을 3부로 확정: (1) 업종별 템플릿 5종(7모듈 표, 빈칸 채우기) (2) 프롬프트 25선(업종마다 정확히 5개씩, 표를 채울 때 바로 쓰는 프롬프트) (3) 실전 체크리스트(오늘/이번 주/이번 달).
- **카테고리 색상을 업종에 직접 매핑**하는 것으로 결정 — 기존 시리즈의 `--cat-a`~`--cat-e`(골드/테라코타/틸/올리브/플럼)를 뷰티·식품·전자기기·서비스·디지털 콘텐츠 5개 업종에 1:1로 고정해서, 섹션 01(업종별 템플릿 워크시트)과 섹션 02(프롬프트 카드)에서 같은 업종이 항상 같은 색으로 보이도록 통일. 이렇게 하면 "본문 디자인 기준"이 요구하는 카테고리 색상 구분이 프롬프트뿐 아니라 워크시트 카드에도 자연스럽게 적용됨.
- CSS 구현: 기존 `.worksheet::before`(왼쪽 골드 바)와 `.worksheet-num`/`.worksheet h4`를 `var(--accent, var(--gold))` 폴백 패턴으로 바꿔서, `.cat cat-b` 등으로 감싼 워크시트는 자동으로 해당 카테고리 색을, 감싸지 않은 워크시트는 기존 골드를 쓰도록 설계 — CSS 규칙 자체는 한 번만 수정하고 마크업에서 래핑 여부로 색을 결정.
- 프롬프트 25개는 Day05 전자책의 18개 범용 프롬프트와 겹치지 않도록, **업종별로 구체화한 프롬프트**(예: 뷰티 "성분→효과 전환", 서비스 "Before/After 사례")로 새로 설계 — 표의 각 모듈과 1:1로 연결되게 각 워크시트 상단에 "관련 프롬프트 BE1~BE5" 식으로 명시.

### 6. PDF 렌더링 및 페이지 여백 검증 — 두 차례 시행착오
- 1차 렌더링(`render_pdf_cloud.js`) 결과 9페이지. `screenshot_pdf_pages_cloud.js`로 전 페이지 스크린샷 확인 중 "01 업종별 템플릿 5종" 헤딩+리드 문단이 페이지 하단에 단독으로 남고 그 아래 약 27~28%가 빈 공간으로 남는 것을 발견(카드 1개가 remaining space에 안 들어가 통째로 다음 페이지로 밀리는, Day01 일지에서 다뤄진 것과 동일 계열 패턴).
- **1차 시도(실패, 되돌림)**: 헤딩+리드+첫 번째 워크시트 카드를 `<div class="chapter-open">`으로 묶고 `break-inside:avoid`를 적용 — 의도는 "헤딩이 카드 없이 혼자 남지 않게" 하는 것이었으나, 실제로는 그룹 전체(헤딩+리드+카드1, 약 540px)가 통째로 다음 페이지로 밀리면서 **오히려 두 페이지에 걸쳐 더 큰 빈 공간(각각 약 43%, 52%)이 새로 생기는** 부작용 발생. `screenshot_pdf_pages_cloud.js`로 재검증 중 발견, 원인은 "워크시트 카드 1개가 이미 페이지의 절반 가까이 차지하는 크기라, 2개를 묶어도 다음 페이지에 남는 공간과 어긋나는" 구조적 문제였음. 즉시 되돌림(`chapter-open` 클래스와 마크업 제거).
- **2차 시도(성공)**: 정밀 측정을 위해 Playwright로 PDF 1~2페이지를 한 번에 담는 세로로 긴 뷰포트(850×2300) 캡처 스크립트를 새로 작성, 페이지 경계(검은 구분선)를 픽셀 단위로 찾아 실제 페이지 높이(767px)와 콘텐츠가 끝나는 지점을 정확히 계산. 빈 공간이 약 212px(27.6%)임을 확인 → 카드를 줄이는 대신 **인트로 문단을 2~3줄 자연스럽게 보강**해서 헤딩 앞의 남는 공간을 채우는 방향으로 수정(사용법 문단 뒤에 "전자책과 함께 보면 좋은 이유" 문장 추가). 재렌더링 후 같은 방식으로 재측정한 결과 빈 공간이 142px(18.5%)로 감소, 30% 기준을 안전하게 통과.
- 전체 9페이지를 다시 스크린샷으로 훑어 템플릿 1+2, 3+4가 각각 같은 페이지에 자연스럽게 붙어 나오는지, 프롬프트 섹션과 체크리스트 섹션에 큰 여백이 없는지 육안 확인 — 문제 없음.
- Day05 일지에서 권장했던 `p{ orphans:1; widows:1; }`를 이번 kit.html에도 기본 포함(누락 상태로 렌더링했다가 뒤늦게 추가 후 재렌더링, 페이지 수는 9페이지로 동일 유지되며 문제 없음 확인).

### 7. 표지 인쇄 폭 검증 및 썸네일 제작
- `scripts/screenshot_element_cloud.js`로 뷰포트 673px(A4 실제 인쇄 폭)에서 `.cover` 캡처, 부제("업종별 템플릿 5종, 프롬프트 25개")와 통계 숫자(5/25/3)가 모두 `.nowrap`으로 감싸져 있어 숫자+단위가 갈라지지 않음을 육안 확인.

## 이슈/트러블슈팅
- **`HEAD detached` 상태로 세션 시작 (5회 연속 재발)**: Day02~05와 동일 패턴. 로컬 HEAD가 origin/main과 완전히 같은 커밋이라 `git checkout -B main origin/main`으로 간단히 정리.
- **"헤딩만 있는 페이지의 빈 공간을 억지로 묶어서 없애려다 더 큰 빈 공간 2개를 새로 만든 사례**: `break-inside:avoid`로 큰 블록들을 강제로 묶는 방식은, 묶인 그룹 자체가 페이지 크기 대비 애매한 비율(정확히 절반보다 살짝 큰 정도)일 때 오히려 문제를 다른 위치로 전이시킬 뿐 해결하지 못함을 확인. **이후 Day에서 유사한 "카드 1개가 페이지의 40~60%를 차지하는" 상황을 만나면, 강제로 묶기보다 먼저 (1) 카드 자체 크기를 줄일 수 있는지, (2) 안 되면 앞쪽 문단 분량을 미세 조정해 헤딩이 시작되는 위치를 옮기는 방향을 먼저 시도할 것.**
- **PDF 페이지 경계/빈 공간을 육안 어림값이 아니라 픽셀 단위로 정밀 측정하는 방법 확립**: `screenshot_pdf_pages_cloud.js`의 연속 스크롤 캡처는 인접 페이지가 한 이미지에 겹쳐 나와 정확한 페이지 높이를 가늠하기 어려웠음. Playwright로 뷰포트를 세로로 크게(850×2300) 잡고 Home 키만 누른 뒤 한 번에 캡처하면, 검은 페이지 구분선의 정확한 y좌표를 Python/Pillow로 스캔해 페이지 높이와 콘텐츠 종료 지점을 픽셀 단위로 계산할 수 있음. 이 방법(스크립트: 세션 스크래치패드의 `tall_capture.js`, 정식 스크립트화하지는 않음)을 이번에 처음 확립 — 다음 Day에서 애매한 여백 판단이 필요하면 재사용 권장.
