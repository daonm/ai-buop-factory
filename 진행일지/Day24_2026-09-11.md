- "2026년 퇴직금 계산 방법" 검색 → 평균임금×30일×(재직일수/365) 공식, 평균임금은 퇴직 전 3개월 급여+상여금·연차수당의 3/12 반영이라는 표준 공식이 그대로 유지되고 있음을 확인.

### 3. 계산기 설계 및 제작 (Python openpyxl)
- 실습자료 지침("코딩 주제면 진짜 동작하는 소스코드, 템플릿 주제면 실제 템플릿 파일")에 따라, 이번 상품은 마크다운 템플릿이 아니라 **수식이 실제로 계산되는 엑셀 파일**이어야 한다고 판단. `pip install openpyxl`로 환경을 갖추고 Python 스크립트(`build_calculators.py`)로 4개 파일을 생성했다.
- 파일 공통 구조를 Day23 전자책 방법 5(기준표를 별도 시트로 분리)·방법 7(면책조항)·방법 9(패키지 구성) 내용을 그대로 반영해 설계: **① 면책조항 시트 → ② 기준표 시트(매년 바뀌는 요율만 분리) → ③ 계산기 시트(입력 셀은 연노랑, 결과 셀은 연올리브 색상 구분)**.
  1. `4대보험료_계산기.xlsx` — 월 급여 입력 시 국민연금(상·하한 적용)·건강보험·장기요양보험·고용보험의 근로자·사업주 부담분을 각각 계산.
  2. `종합소득세_예상세액_계산기.xlsx` — 연 수입·필요경비·소득공제 입력 시 8단계 세율표를 `VLOOKUP` 근사매칭으로 적용해 과세표준·산출세액·지방소득세를 계산하고, 3.3% 원천징수 기납부세액과 비교해 환급/추가납부 예상액까지 계산.
  3. `퇴직금_계산기.xlsx` — 퇴직 전 3개월 급여·상여금·연차수당·재직일수 입력 시 평균임금을 계산하고, 통상임금과 비교해 더 큰 값을 기준으로 퇴직금을 산출.
  4. `급여명세서_자동생성_시트.xlsx` — 기본급·각종 수당을 입력하면 4대보험 공제와 근로소득세 근사치, 지방소득세까지 자동 계산해 실수령액을 뽑는 실무형 양식.

### 4. 수식 검증 — LibreOffice 재계산 실패 → Python 재구현으로 교차검증, 실제 버그 발견
- 처음엔 `soffice --headless --convert-to`로 파일을 열어 강제 재계산시켜 검증하려 했으나, 이 샌드박스 환경에서는 LibreOffice가 **어떤 파일도(간단한 xlsx, 심지어 txt조차) 열지 못하는 상태**임을 확인 (`Error: source file could not be loaded`, UserInstallation 프로필을 새로 만들거나 로케일을 바꿔도 동일). `poppler-utils`는 apt로 설치에 성공했지만 LibreOffice 자체의 파일 로딩 문제는 원인을 특정하지 못해 우회하기로 결정.
- 대신 각 계산기의 수식 로직을 Python으로 동일하게 재구현해 기본 입력값으로 결과를 계산하고, 크기·부호가 상식적인 범위인지(예: 실수령액이 총급여의 약 90% 수준인지) 직접 검산했다.
- 이 과정에서 **`급여명세서_자동생성_시트.xlsx`의 공제 계산 수식이 기준표 시트의 행 번호와 어긋나 있는 실제 버그를 발견**했다. `4대보험료_계산기.xlsx`의 기준표(요율 10개 항목)를 만들 때 썼던 셀 참조를, 항목 수가 다른(8개 항목) `급여명세서` 기준표에 그대로 복사해서 썼던 것이 원인 — 예를 들어 건강보험료 계산식이 실제로는 "국민연금 하한액(40만원)"을 요율처럼 곱하고 있었다. 행 배치를 주석으로 명시해두고 참조를 전부 다시 맞춘 뒤 재검증해서 정상 계산됨을 확인했다(기본급 330만원 기준 실수령액 2,848,872원으로 상식적인 비율 확인).
- 4개 파일 모두 기본 입력값 기준 검산 결과를 `kit.html`의 "계산기 4종 빠른 참고표"에 실제 숫자로 그대로 인용해, 구매자가 같은 값을 넣어보면 동일한 결과가 나오는지 스스로 재현·확인할 수 있게 했다.

### 5. kit.html 제작 — Day02/Day22 디자인 패턴 재사용

### 6. PDF 렌더링 및 검증
- `render.js`(Playwright, `/opt/pw-browsers` Chromium)로 `kit.html`을 A4(여백 18mm/16mm)로 PDF 변환. `poppler-utils`를 apt로 새로 설치해 `pdftoppm`으로 각 페이지를 PNG로 렌더링한 뒤 5페이지 전부 육안 확인.
  - 총 5페이지(표지 1 + 본문 3 + 체크리스트·에필로그 1).
  - 표지(1p)와 마지막 에필로그 페이지(5p)는 지침대로 정상적인 여백(책 표지·마지막 장 관례).
  - 본문 중간 페이지(2~4p)는 카드가 페이지 하단까지 고르게 채워져 큰 빈 공간 없음을 확인. 3페이지 끝에 다음 섹션(02)이 시작되기 전 약 25% 정도의 여백이 있었으나 30% 기준 이내이고 섹션 경계에서 자연스럽게 생기는 정도라 판단해 추가 조정 없이 통과.
- `.cover`를 673px 뷰포트(A4 실제 인쇄 폭 근사치)로 스크린샷해 표지 문구 확인 — 부제의 "4종", 하단 숫자 배지의 "2026년 기준표" 등 숫자+단위 조합이 모두 `nowrap` 처리돼 있어 어색하게 끊기는 곳 없음을 확인.

- 별도 이미지 생성 도구 없이, 지침대로 `kit.html`의 `.cover` 요소를 Playwright로 1000×1000 뷰포트·`deviceScaleFactor: 2`로 스크린샷 캡처해 `marketing/thumbnail.png` 생성(실제 저장 크기 1600×1254, Day23 썸네일과 동일한 캡처 방식). 클립아트·이모지·네온 효과 없이 책 표지와 완전히 동일한 에디토리얼 톤 유지.

## 이슈/트러블슈팅
- **LibreOffice 헤드리스 변환 완전 실패**: `soffice --headless --convert-to`가 xlsx는 물론 최소한의 txt 파일조차 "source file could not be loaded" 오류로 열지 못했다. UserInstallation 프로필을 새로 만들거나(`-env:UserInstallation=file:///tmp/...`) 로케일을 바꿔봐도 동일 — 이 클라우드 세션 환경 자체에 LibreOffice 실행 환경 문제가 있는 것으로 추정된다. 근본 원인은 못 찾았고, 대신 Python으로 동일 수식 로직을 재구현해 결과값을 검산하는 방식으로 우회했다. **다음에 엑셀 파일을 다루게 되면 이 환경에서 LibreOffice 변환이 다시 안 될 가능성이 높다는 점을 감안하고, 처음부터 Python 재구현 검산을 병행할 것.**
- **기준표 행 번호 참조 버그**: 4개 파일 중 `급여명세서_자동생성_시트.xlsx`에서, 다른 파일(`4대보험료_계산기.xlsx`)의 기준표 행 배치를 그대로 복사해 셀 참조를 쓰다가 실제 계산이 틀어지는 버그가 있었다. LibreOffice로 즉시 재계산해서 눈으로 확인하는 안전망이 없었기 때문에, Python 재구현 검산 단계에서 걸러내지 못했다면 그대로 판매됐을 수도 있는 문제였다. **엑셀 수식을 생성 스크립트로 만들 때는 시트마다 기준표 행 배치를 주석으로 먼저 명시하고, 파일 간 셀 참조를 복사-붙여넣기 하지 않는 습관이 필요하다.**
- `poppler-utils` 미설치 상태였으나 `apt-get update && apt-get install -y poppler-utils`가 정상 동작해 `pdfinfo`/`pdftoppm`으로 정확한 페이지 수·페이지별 이미지를 확보할 수 있었다 — Day21~23에서 poppler 없이 정규식으로 페이지 수를 근사했던 것보다 훨씬 신뢰도 높은 검증이 가능했다. **다음 Day부터는 세션 시작 시 poppler-utils 설치를 먼저 시도할 것.**
