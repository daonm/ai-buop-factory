### 3. 예시 거래내역 데이터셋 설계 및 검산
- 계산기 간(A→B→C) 입력값이 서로 이어지는 하나의 일관된 예시가 필요해, 애플 50주(2개 Lot: 25주@$130·25주@$150) 매수 후 30주만 매도(선입선출법 vs 이동평균법 차이를 보여주기 위해 "전량 매도"가 아닌 "부분 매도"로 설계), 테슬라 15주 전량 매도(손실 사례)로 구성된 예시 데이터셋을 직접 설계.
- Python으로 먼저 손계산 검증: 애플 이동평균 취득원가(30주) 5,558,874원 → 양도차익 5,340,126원, 선입선출 취득원가(Lot1 25주 전량+Lot2 5주) 5,267,342원 → 양도차익 5,631,658원(차이 291,532원), 테슬라 양도차손 -1,012,820원 → 손익통산 합계 4,327,306원 → 기본공제 250만 원 적용 과세표준 1,827,306원 → 양도소득세(20%) 365,461원+지방소득세(2%) 36,546원 = 최종 납부세액 402,007원. 이 숫자를 kit.html 빠른 참고표·엑셀 샘플 행·마케팅 카피(threads_posts.md 제작과정형 글)에 일관되게 사용.
- 처음에는 애플 매도가를 $210으로 설계했다가 손익통산 후 과세표준이 0원(기본공제 이하)이 되는 것을 확인 — "세금이 얼마 나오는지 보여주는" 예시로는 설득력이 약하다고 판단해 매도가를 $260으로 올려 재계산, 최종적으로 402,007원이라는 0이 아닌 최종세액이 나오도록 조정.

### 4. 환경 준비 — 파이썬 패키지
- `python3 -c "import openpyxl"` → `ModuleNotFoundError`. `pip install openpyxl python-docx` 실행 시 "Requirement already satisfied"로 나왔는데도 같은 오류가 반복돼, `which python3`/`python3 --version`으로 확인한 결과 기본 `python3`는 3.11이고 `pip`(시스템 `/usr/bin/pip`)는 python 3.13 쪽 dist-packages에 설치하고 있었음(멀티 파이썬 버전 컨테이너). `python3.11 -m pip install openpyxl python-docx`로 3.11 쪽에 명시적으로 설치해 해결. 이후 모든 스크립트는 `python3.11 -I`로 실행(스크래치패드 스크립트 격리 원칙 준수).

### 5. 엑셀 계산기 4종 제작 및 수식 검증
- `openpyxl`로 A~D 4개 xlsx 파일 생성 스크립트(`/tmp/.../scratchpad/build_xlsx.py`) 작성. 안내 시트(경계 문구) + 계산기 시트(노란 입력칸/올리브 결과칸, 데이터 유효성 드롭다운) 공통 구조로 제작.
  - **A. 해외주식_거래내역통합_환율환산_계산기.xlsx** — 증권사·종목·구분(매수/매도, 드롭다운)·거래일·거래가(외화)·거래환율·수량·수수료(외화)를 입력하면 거래금액(원)·수수료(원)·거래금액(수수료반영,원, `IF(구분="매수",+,-)`)이 자동 계산되고, 하단 `SUMIFS` 종목별 합계표로 여러 증권사(토스증권/미래에셋증권/삼성증권) 거래가 자동 합산되는지 확인.
  - **B. 취득원가_종목별손익_손익통산_계산기.xlsx** — 매수 Lot별 입력(종목·Lot번호·매수일·매수가·환율·수량·수수료) → Lot단가 자동 계산 → 이동평균법 구간(`SUMIF`로 총매수수량·총매수금액 집계 후 평균단가×매도수량) → 선입선출법 비교 구간(Lot별 배분수량을 사용자가 직접 입력하면 `SUMPRODUCT` 방식 대신 Lot별 원가를 개별 계산 후 합산, 배분합계가 매도수량과 일치하는지 안내) → 종목별 손익 요약(적용방식 드롭다운으로 이동평균/선입선출 선택) → 손익통산 합계(`SUM`)까지 5단계 구성.
  - **C. 기본공제_세율적용_최종세액_계산기.xlsx** — 손익통산 합계 입력 → 기본공제(250만 원, `MAX(0,손익-공제)`) → 양도소득세(20%)·지방소득세(2%) → 최종 납부세액. "본인" 블록과 동일 구조의 "가족 구성원(배우자 등)" 블록을 별도로 둬 기본공제가 1인당 연 1회 별도 적용됨을 수식으로도 보여줌.
  - **D. 신고기한Dday_신고서류체크리스트.xlsx** — 'D-day계산기' 시트(거래발생연도 입력 → `DATE(연도+1,5,31)`로 마감일, `TODAY()`·마감일 차이로 남은 일수 자동 계산 + 가산세 리스크 요약 표) + '체크리스트' 시트(기본/거래내역/계산근거/제출증빙 4개 구분, 서류 20종, 준비상태 드롭다운).
- openpyxl은 수식을 계산하지 않고 저장만 하므로, 컨테이너에 설치된 `libreoffice`(`soffice --headless --convert-to xlsx`)로 4개 파일을 재저장시켜 강제로 재계산시킨 뒤 `openpyxl(data_only=True)`로 다시 읽어 결과값을 전수 검증. 처음 CSV로 변환을 시도했다가 한글 파일명 인코딩 문제로 저장 실패를 겪어, ASCII 파일명(`a.xlsx`~`d.xlsx`)으로 복사 후 xlsx 포맷으로 재변환하는 방식으로 전환해 해결. 검증 결과 모든 계산값이 3단계에서 손계산한 숫자(5,558,874 / 5,340,126 / 5,267,342 / 5,631,658 / 291,532 / -1,012,820 / 4,327,306 / 1,827,306 / 365,461 / 36,546 / 402,007)와 정확히 일치함을 확인. D-day계산기는 처음 거래발생연도 기본값을 2025로 뒀더니 오늘(2026-10-29) 기준 마감일(2026-05-31)이 이미 지나 남은 일수가 음수(-151일)로 나오는 것을 발견 — 기본값을 2026(마감일 2027-05-31)으로 수정해 "다가오는 기한"을 보여주는 예시로 재조정.

## 이슈/트러블슈팅
- 컨테이너에 파이썬이 여러 버전(3.11/3.12/3.13) 설치돼 있었고, 기본 `python3`(3.11)와 시스템 `pip`(3.13 dist-packages)가 서로 다른 버전을 가리켜 `pip install`이 "이미 설치됨"이라 보고해도 `python3 -c "import openpyxl"`은 계속 실패하는 상황을 겪음. `python3.11 -m pip install`로 실행 중인 인터프리터에 명시적으로 설치해 해결 — 다음에 유사 상황이면 `pip`/`pip3` 대신 항상 `python3 -m pip install`(또는 실제 사용할 인터프리터 명시)로 설치할 것을 메모.
- `soffice --convert-to csv`로 xlsx 수식 검증을 시도했다가 한글 파일명이 포함된 출력 경로에서 "Please verify input parameters" 오류로 저장 실패 — ASCII 파일명으로 복사 후 xlsx 포맷으로 재변환(`soffice --convert-to xlsx`)하는 방식으로 전환해 해결. 이후 Day마다 한글 파일명의 xlsx를 LibreOffice로 재계산 검증할 때는 ASCII 임시 파일명을 거치는 것을 표준 절차로 메모.
- **본문 중간 페이지 빈 공간 문제가 실제로 재현됨** — Worksheet 카드의 `break-inside:avoid`가 원인이었고, padding/margin을 더 줄이는 것만으로는 해결되지 않아 해당 속성 자체를 제거(행 단위 자연스러운 분할 허용)하는 방식으로 해결. 작업 지침에 예시로 언급된 Day02(2026-08-21)의 문제와 동일한 유형이 이번에도 발생한 것으로, "PDF 렌더링 후 반드시 각 페이지를 넘기며 육안 확인"하는 절차가 실제로 유효했음을 재확인.
- `/opt/pw-browsers/chromium-1243`의 실제 디렉터리명이 `chrome-linux64`(기존 스크립트 기본 탐색 경로인 `chrome-linux`가 아님)라 `PLAYWRIGHT_CHROMIUM_PATH` 환경변수를 매번 명시적으로 지정해야 했음 — Day67·69·70에서도 반복된 패턴.
