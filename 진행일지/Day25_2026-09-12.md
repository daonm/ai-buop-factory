### 6. PDF 렌더링 및 페이지 검증 — 실제로 여백 버그 발견·수정
- `poppler-utils`가 이 세션에 설치돼 있지 않아 `apt-get install -y poppler-utils`로 새로 설치 (Day24 로그의 권고대로 세션 시작 시 먼저 설치).
- `scripts/render_pdf_cloud.js`로 1차 렌더링 → 14페이지. `pdftoppm`으로 전 페이지 PNG 추출 후, 육안 확인 대신 **Python(PIL/numpy)으로 각 페이지 하단 여백 비율을 정량 측정하는 스크립트**를 즉석에서 작성해(행별 최소 밝기값으로 마지막 텍스트/라인 위치를 찾고 페이지 하단 여백까지의 픽셀 비율 계산) 14페이지 전체를 자동 스캔.
- **1차 스캔 결과 12페이지에서 33.4% 하단 여백 발견** — "바로 쓰는 프롬프트 16선" 섹션에서 D 카테고리("영업·운영")의 `.cat-label`만 12페이지 하단에 렌더링되고, 그 아래 `.prompt-grid`(4개 프롬프트 카드)는 통째로 13페이지로 넘어가면서 라벨과 콘텐츠가 분리되고 12페이지 하단이 크게 비는, 진행일지 Day01의 13~14번 항목에서 이미 겪었던 것과 같은 유형의 버그였음.
- **원인**: `.prompt-block`에는 `break-inside:avoid`가 걸려 있지만 카테고리 블록(`.cat` 전체, 라벨+그리드)에는 여백을 관리할 규칙이 없어서, 카테고리 전환 시점에 남은 페이지 공간이 라벨만 겨우 들어가고 그리드 첫 행은 못 들어가는 애매한 경우 이런 분리가 발생함.
- **수정**: `.prompt-block` padding(10px 12px 11px → 8px 10px 8px), `.prompt-grid` gap(9px→7px)·margin-bottom(20px→13px), `.cat` margin-bottom(8px→6px), `.cat-label` margin(12px→8px)·padding(5px 12px→4px 12px), `.prompt` 코드블록 padding(9px 11px→7px 9px)·font-size(0.78rem→0.76rem)를 전반적으로 타이트하게 조정해 카테고리 4개(A~D) 전체가 12페이지 안에 다 들어가도록 만듦. 재렌더링 결과 12페이지 여백이 2.7%로 줄고 D 카테고리 전체가 정상적으로 12페이지에 들어감.
- **2차 이슈**: 이 수정으로 이번엔 에필로그의 마지막 문장 뒤 "— 끝 —" 서명 한 줄만 13페이지에서 분리돼 14페이지 전체가 거의 빈 채로 남는 문제가 새로 나타남(97.5% 여백). 처음엔 `.epilogue` 전체에 `break-inside:avoid`를 걸었으나, 에필로그 전체(두 문단+서명)를 통째로 다음 페이지로 미는 방식이라 13페이지 여백이 오히려 41.5%로 커지는 부작용 발생 — Day01 로그의 "큰 컨테이너에 break-inside:avoid를 걸면 안 된다"는 교훈을 다시 확인.
- **최종 수정**: 에필로그를 첫 문단(자유롭게 페이지 분할 허용)과, 두 번째 문단+서명을 묶은 `.epilogue .close`(작은 단위, `break-inside:avoid`)로 나눠 구조를 변경. 재렌더링 결과 13페이지 여백 23.0%(기준 30% 이내)로 안정, 14페이지(에필로그 마무리, 90.4% 여백)는 표지와 마찬가지로 책의 마지막 장 관례로 허용 범위로 판단(Day23 로그에서도 같은 기준 적용).
- **최종 검증**: 정량 스캔으로 전체 14페이지 중 표지(1p, 38.8%)와 마지막 에필로그(14p, 90.4%)를 제외한 모든 본문 페이지가 30% 미만의 하단 여백을 유지함을 확인. 추가로 각 페이지를 Read 툴로 직접 열어 육안으로도 재확인.

## 이슈/트러블슈팅
- **HEAD detached 상태로 세션 시작**: 이전 여러 Day에서 반복되는 패턴. `git fetch origin main && git checkout main && git merge --ff-only origin/main`으로 매번 해결 가능하나, 다음 세션에서도 반복될 가능성이 높으므로 세션 시작 직후 항상 이 절차부터 실행할 것.
- **프롬프트 카테고리 블록의 라벨-콘텐츠 분리 버그(신규 유형)**: Day01에서 정리한 "큰 컨테이너에 break-inside:avoid를 걸면 안 된다"는 교훈이 이번엔 다른 형태로 재발했다 — 이번엔 반대로 컨테이너에 아무 보호 규칙이 없어서 라벨과 콘텐츠가 페이지 경계에서 분리되는 문제였다. `.prompt-block` 개별 카드에는 `break-inside:avoid`가 있었지만, `.cat`(카테고리 라벨+그리드 묶음)에는 아무 규칙이 없어 라벨만 남고 그리드가 통째로 다음 페이지로 밀리는 경우가 생겼다. **해결책은 컨테이너에 무작정 break-inside:avoid를 거는 게 아니라, 콘텐츠 전체(A~D 4개 카테고리)가 페이지 안에 다 들어가도록 카드 padding·gap을 전반적으로 줄여 여유 공간을 만드는 것**이었다. 다음에 같은 4카테고리×4프롬프트 구조를 쓸 때는 처음부터 이번에 정리한 수치(prompt-block padding 8px 10px 8px, grid gap 7px, cat margin-bottom 6px, cat-label margin-bottom 8px)를 기본값으로 적용할 것.
- **에필로그 서명 줄 고아(orphan) 문제**: 에필로그 전체에 break-inside:avoid를 걸면 오히려 이전 페이지 여백이 커지는 역효과가 남을 재확인. 마지막 문단+서명처럼 "짧고 반드시 붙어있어야 하는 꼬리 부분"만 별도로 작은 wrapper(`.epilogue .close`)로 묶어 break-inside:avoid를 적용하는 방식이 더 안전하다는 걸 확인했다. **앞으로 에필로그류 마무리 섹션을 만들 때는 처음부터 이 구조(첫 문단 자유 + 마지막 문단·서명 묶음)를 기본값으로 쓸 것.**
- **여백 육안 확인을 정량화**: 이번에 처음으로 "각 페이지 하단 텍스트/라인의 마지막 위치를 픽셀 단위로 찾아 여백 비율을 계산"하는 Python 스크립트를 즉석에서 만들어 14페이지 전체를 몇 초 만에 스캔했다. 기존에는 Read 툴로 페이지를 하나씩 열어보며 육안 판단에 의존했는데, 이 방식이 훨씬 빠르고 객관적이었다. **다음 Day부터는 PDF 페이지 검증 시 이 정량 스캔을 먼저 돌려 30% 초과 페이지만 골라 육안으로 재확인하는 순서로 진행할 것** (스크립트는 저장해두지 않고 매번 인라인으로 작성했으므로, 자주 쓴다면 `scripts/`에 정식으로 저장하는 것을 고려할 만함).
