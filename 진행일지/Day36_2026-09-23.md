### 3. 계산기 4종 설계 및 openpyxl로 제작
전자책 방법을 각각 독립된 엑셀 파일로 구현(Day34가 4개 파일로 나눈 방식과 동일):
- **A. 대출상환_비교_계산기.xlsx** — 원금·연이율·상환개월수를 입력하면 원리금균등상환(PMT 공식)과 원금균등상환(균등 원금 + 잔액 기준 이자) 두 방식의 월상환액·총이자를 자동 비교하고, 1~12회차 상환 스케줄을 두 방식 나란히 산출. 원금균등 총이자는 `월이율×원금×(개월수+1)/2` 폐쇄형 공식으로 계산(등차수열 합 공식에서 유도).
- **B. 대환대출_순이익_계산기.xlsx** — 기존·신규 대출의 PMT 차이로 "아끼는 총이자"를 구하고, 중도상환수수료(경과개월수·감면기간 기준 선형 체감 구조)와 신규 대출 부대비용을 뺀 순이익, 손익분기 개월수를 계산. 여러 은행 후보 2~3곳을 나란히 비교하는 표 포함. 별도 "중도상환수수료 기준표" 시트에 변동/고정금리 수수료율 차이와 감면 구조를 정리.
- **C. 전월세전환율_계산기.xlsx** — 줄이는 보증금·전환율을 입력하면 월세를 계산하고, 한국은행 기준금리 기반 법정 상한(MIN(기준금리+2%p, 10%))과 비교해 갱신/신규 계약별 적법 여부를 자동 판정. 보증금 감액 구간(1천만~1억)별 시뮬레이션 표 포함. "전환율 기준표" 시트에 법정 상한 공식과 시장 평균 참고치 정리.
- **D. 전세갱신_상한_계산기.xlsx** — 기존 보증금·요구 인상액을 입력하면 갱신청구권 5% 상한 기준 적법 여부를 판정하고 초과 금액을 계산. 인상분을 전액 보증금/절반씩/전액 월세전환하는 3가지 분산 시나리오의 초기 목돈 부담·월 부담 증가를 비교.

Python(openpyxl)으로 4개 파일을 생성하는 빌드 스크립트를 세션 스크래치패드에 작성해 실행(Day34 선례를 따라 저장소에는 커밋하지 않음).

### 4. 계산기 값 검증 — LibreOffice 재확인, 이번에도 실패
- Day34 진행일지에서 이미 "LibreOffice headless 변환이 이 클라우드 세션에서 깨져있다"고 기록해뒀는데, 이번 세션에서 환경이 갱신됐는지 다시 확인해봤다. `soffice --headless --convert-to xlsx`로 방금 openpyxl로 만든 파일뿐 아니라 `/tmp`에 복사한 최소 파일까지 시도했으나 여전히 `Error: source file could not be loaded`로 실패 — Day34와 동일하게 이 클라우드 이미지의 LibreOffice 설치 자체가 깨져있는 것으로 재확인.
- 대신 순수 Python으로 각 계산기의 핵심 수식을 동일한 기본값으로 재계산해 교차검증:
  - A: 원금 3억·연이율 4.5%·360개월 → 원리금균등 월상환액 1,520,056원, 총이자 차액(원리금균등−원금균등) 44,157,635원.
  - B: 기존 4.8%→신규 3.9%, 잔액 3억·남은 240개월, 중도상환수수료 14개월 경과/수수료율 1.2%/감면 36개월, 부대비용 50만원 → 아끼는 총이자 34,728,102원, 수수료 2,200,000원, 순이익 32,028,102원, 손익분기 18.7개월.
  - C: 보증금 5천만원·전환율 5.5%·기준금리 3.0% → 월세 229,167원, 법정 상한 전환율 5.0%, 상한 월세 208,333원.
  - D: 기존 보증금 3억·요구 인상액 2천만원 → 상한 1,500만원(5%), 초과 500만원, 시나리오 B(절반 월세전환)의 월 증가액 34,375원.
  - 모든 값이 상식적인 범위(3억 대출에 월 150만원대 상환액, 5천만원 보증금 감액에 월 20만원대 월세 등)에 들어 계산식이 논리적으로 올바름을 확인. 수식 문법 자체는 Day34에서 이미 실제 판매용으로 검증된 셀 참조 패턴(`=B4*B9*(1+B9)^B6/((1+B9)^B6-1)` 형태)을 그대로 재사용했으므로 Excel/Google 시트에서 정상 작동할 것으로 판단.

### 7. PDF 렌더링 및 페이지 여백 검증
- `scripts/render_pdf_cloud.js`로 렌더링 → **6페이지** 생성(Day34의 5페이지와 비슷한 분량). `pdftoppm`이 이번 세션에는 설치돼 있지 않아 `scripts/screenshot_pdf_pages_cloud.js`(Chrome 내장 PDF 뷰어를 스크롤하며 캡처)로 페이지별 이미지를 확보했는데, 뷰포트 높이가 페이지 높이보다 약간 커서 PageDown 한 번에 페이지가 1개 이상씩 건너뛰는 현상이 있어 `scan_page_margins.py`의 정량 스캔이 무의미해짐(중복 캡처된 페이지들이 전부 마지막 페이지로 나옴). 대신 Read 툴로 고유한 페이지 이미지(1, 2, 3, 4/5(체크리스트+에필로그))를 직접 열어 육안 확인.
- 표지(1p)는 독립 페이지로 정상. 2~3p(개요+섹션01 계산기 4종 참고표)는 카드/표가 페이지 경계에서 자연스럽게 이어지고 큰 빈 공간 없음. 4p(섹션02 워크시트+섹션03 체크리스트 시작)도 정상. 5p(체크리스트 나머지 4단계)+6p(에필로그)는 체크리스트가 거의 한 페이지를 채우고 에필로그는 짧은 클로징 문구만 있어 하단이 비는 것을 확인했으나, 이는 책 말미 에필로그의 통상적인 여백(Day34에서도 동일 패턴 확인됨)이라 "본문 중간 카드 사이 빈 공간" 문제에 해당하지 않는다고 판단.

## 이슈/트러블슈팅
- **LibreOffice headless 변환이 이 클라우드 세션에서도 여전히 깨져있음** — Day34에서 처음 발견한 문제가 재현됨(3번째 확인 아님, Day35는 xlsx가 없어 겪지 않음). 최소 예제 파일도 "source file could not be loaded"로 실패. **다음에 엑셀 계산기를 만들 때도 처음부터 손계산 검증 경로로 계획할 것** — 매 세션 재시도로 시간 낭비하지 말고, 이 진행일지와 Day34 진행일지에 남긴 기록을 참고해 바로 손계산으로 넘어갈 것.
- **`screenshot_pdf_pages_cloud.js`의 PageDown 스크롤 방식이 6페이지짜리 짧은 문서에서는 페이지를 건너뛰는 문제**: 뷰포트(850×1250)가 A4 한 페이지보다 약간 커서, 한 번의 PageDown이 페이지 경계를 넘어 다음 페이지 중간까지 스크롤되는 경우가 있어 이후 스크린샷이 전부 마지막 페이지로 중복 캡처됨. 짧은 문서(10페이지 미만)를 검증할 때는 이 스크립트의 자동 정량 스캔(`scan_page_margins.py`)을 그대로 신뢰하지 말고, 고유 해시를 가진 이미지만 골라 Read 툴로 직접 확인하는 방식을 병행할 것. **원인(뷰포트/페이지 비율 미세 오차) 자체를 스크립트에서 고치는 건 이번 세션 범위를 벗어난다고 판단해 보류.**
- DSR·대출한도 계산기(전자책 방법8)와 전세 vs 월세 비교(방법7)는 로드맵 표 제목이 명시한 "대출상환·전월세 전환" 두 영역에 맞춰 이번 4종에서 의도적으로 제외함 — 빠뜨린 것이 아니라 범위를 좁힌 결정이므로, 추후 반응이 좋으면 "DSR·대출한도 계산기" 또는 "전세 vs 월세 총비용 계산기"를 별도 보너스 상품으로 추가하는 것을 고려할 수 있음.
