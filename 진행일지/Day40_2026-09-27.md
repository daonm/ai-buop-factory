## 진행 과정

### 1. 저장소 상태 점검 — 이번에도 detached HEAD + 4일치 미푸시 커밋 발견
- 세션 시작 시 로컬 HEAD가 `refs/heads/main`과 분리된 detached 상태였고, `git log`로 확인하니 이 detached HEAD(Day39까지 완료)가 로컬 `main` 브랜치보다 8커밋(Day36~39) 앞서 있었다. 반면 로컬 `main`과 `origin/main`은 Day35에 멈춰 있었다 — 즉 지난 세션들에서 작업은 계속 진행됐지만 `main` 브랜치로 병합·푸시가 안 되고 있었던 것으로 보인다.
- `git merge-base --is-ancestor origin/main HEAD`로 순수 fast-forward 관계임을 먼저 확인한 뒤, `git checkout main` → `git merge --ff-only <detached HEAD>` → `git push origin main`으로 Day36~39 커밋을 모두 `main`에 반영하고 원격에 푸시. `git fetch` 후 `origin/main`·`main`·이전 detached HEAD 세 커밋 해시가 모두 일치함을 재확인해 데이터 유실 없이 복구됐음을 검증했다.
- **다음 세션을 위한 메모**: 매 세션 시작 시 `git status`뿐 아니라 `git log --oneline -3`과 `git log main --oneline -3`을 함께 확인해 HEAD가 `main`과 같은 커밋을 가리키는지, `origin/main`과 얼마나 차이 나는지 점검하는 습관이 필요하다. 이번처럼 어긋나 있으면 fast-forward 가능 여부를 먼저 확인한 뒤 병합·푸시할 것.

### 3. 계산기 3종 + 템플릿 1종 + 체크리스트 1종 설계 및 openpyxl로 제작
`pip install openpyxl`로 환경에 설치 후, Python 빌드 스크립트를 세션 스크래치패드에 작성해 실행(저장소에는 커밋하지 않음). 공통 스타일 헬퍼 함수(제목/섹션/라벨/입력셀/결과셀/헤더행/노트)를 만들어 5개 파일에 일관 적용.
- **A. 니치별_RPM_수익성_계산기.xlsx** — 니치 3개의 RPM 하단/상단을 입력하면 월 조회수 1만/10만/100만 구간별 예상 광고수익을 `TEXT()` 함수로 "하단~상단원" 문자열로 계산, 니치 간 최대/최소 RPM 배율, 목표 월 광고수익 달성에 필요한 조회수 역산까지 포함.
- **B. YPP_달성_로드맵_계산기.xlsx** — 기준값 섹션에 2026년 9월 확인 기준 YPP 조건(펜 펀딩: 구독자 500명+90일 3,000시간 또는 쇼츠 300만 회, 전체 광고수익: 구독자 1,000명+4,000시간 또는 쇼츠 1,000만 회, 2027년 2월 기준 상향 예고)을 명시. 롱폼 경로(주당 업로드·평균 조회수·시청 지속시간·구독 전환율 입력 → 월 시청시간·월 신규구독자 계산 → 각 조건 도달 예상 개월수 역산)와 쇼츠 경로(쇼츠 업로드·조회수 입력 → 누적 조회수 기준 도달 개월수)를 나란히 계산해 더 빠른 경로를 비교할 수 있게 구성.
- **C. 협찬단가_제휴수익_계산기.xlsx** — 구독자·평균 조회수·참여율·기준 단가(원/1,000뷰) 입력 시 참여율 구간별(6%↑/4%↑/2%↑/미만) 보정 배율을 IF 중첩으로 계산하고, 언급형(1.0배)·전용리뷰형(1.6배)·콜라보형(2.4배) 3개 영상 유형별 협찬 단가를 동시에 산출. 하단에 제휴마케팅(클릭률×전환율×수수료) 월 예상 수익 계산과 채널 성장 단계별(0~1천/1천~1만/1만 이상) 수익원 도입 로드맵 표를 추가.
- **D. 채널기획서_4주캘린더_영상아이디어30개.xlsx** — 계산 파일이 아니라 AI 리서치 결과를 옮겨 적는 4개 시트(안내/채널기획서/4주캘린더/영상아이디어30개) 템플릿. 채널기획서 시트는 채널명 후보 3·타깃 페르소나 3·핵심 시리즈 4를 입력하는 표, 4주캘린더는 8행(4주×2회)의 주차별 표, 영상아이디어30개는 30행 입력 표 + 난이도(바로 찍을 수 있음/준비가 필요함) `COUNTIF` 자동 집계를 하단에 배치해 순수 빈 양식이 아니라 "계산기스러운" 요소를 하나 남겼다.

### 4. 계산기 값 검증 — LibreOffice headless 변환 5번째 세션째 동일 실패 재확인
- `pip install openpyxl` 직후 `soffice --headless --convert-to xlsx`로 방금 만든 계산기 파일을 재계산 시도 → `Error: source file could not be loaded`로 실패. 파일명을 ASCII로 바꾸고 `-env:UserInstallation`으로 격리된 프로필을 지정해도 동일하게 실패, PDF 변환도 동일 에러. **Day34·36·38 진행일지에 이미 3회 연속 실패가 기록돼 있었는데 이번이 4번째(통산 5번째 세션) 재확인** — 이 클라우드 환경의 구조적 문제로 최종 확정하고, 더 이상 재시도하지 않고 곧바로 손(Python) 계산 검증으로 전환.
- 순수 Python으로 각 계산기의 핵심 수식을 동일한 기본값으로 재계산해 교차검증:
  - A: 재테크(3,000~8,000원) 니치 월 10만 조회 → 300,000~800,000원(일치). 재테크 대비 브이로그(800~1,500원) 배율 = 8,000/1,500 ≈ 5.3배(일치).
  - B: 주 2회 업로드·평균 3천회·시청 4분 → 월 8.6편, 월 시청시간 1,720시간, 월 신규구독자 129명 → 구독자 500명 도달 500/129≈3.9개월(일치), 3,000시간 도달 3000/1720≈1.7개월. 쇼츠 주5회·평균8천회 → 월 172,000회 → 300만회 도달 약 17.4개월(일치).
  - C: 구독자5천·조회수4천·참여율4.0% → 보정배율 1.15배(4% 이상 구간). 전용리뷰형(1.6배) 기본단가 96,000원×1.15=110,400원(일치). 제휴마케팅: 월4편×4000회×3%×5%×3000원=72,000원(일치).
  - 모든 값이 상식적인 범위에 들어 수식이 논리적으로 올바름을 확인.

### 7. PDF 렌더링 및 페이지 여백 검증
- `scripts/render_pdf_cloud.js`로 렌더링 → **7페이지** 생성(raw PDF의 `/Count 7`로 확인 — 이 클라우드 환경엔 `pdfinfo`/`pdftoppm`(poppler-utils)이 설치돼 있지 않아 `pip install pillow numpy`로 PIL 기반 대체 검증 경로를 사용, `pypdf`는 `cryptography` 바인딩 오류로 설치 실패해 페이지 수는 raw PDF 바이트에서 `/Count` 값을 grep해 확인).
- `scripts/screenshot_pdf_pages_cloud.js`(Chrome 내장 PDF 뷰어 스크롤 캡처)로 7페이지 전부 캡처 후, `scan_page_margins.py`(PIL/numpy)로 정량 스캔 — 뷰포트가 페이지 경계와 정확히 안 맞아 전 페이지 `bottom_empty_ratio=0.000`으로 나와 스캔 자체는 참고용에 그쳤고, Read 툴로 1·3·5·7페이지를 직접 열어 육안 확인했다. 표지(1p)는 독립 페이지로 정상. 3p(섹션01 계산기 참고표, cat-a/b/c/d 도메인 블록)는 색상 구분 카드가 자연스럽게 이어지고 빈 공간 없음. 5p(상담 진행 체크리스트 task-grid 2단 배치, 3그룹)도 온보딩·채널기획·납품 그룹이 색상별로 선명히 구분되며 빈 공간 없이 이어짐. 7p(에필로그)는 짧은 클로징 문구만 있어 마지막 페이지 하단이 비는데, 이는 Day34·36·38에서도 동일하게 확인된 책 말미 에필로그의 통상적인 여백이라 "본문 중간 카드 사이 빈 공간" 문제에 해당하지 않는다고 판단.

## 이슈/트러블슈팅
- **세션 시작 시 로컬 HEAD가 detached였고, `main` 브랜치가 4일치(Day36~39) 뒤처져 있었으며 원격에도 푸시가 안 돼 있었음.** `git merge-base --is-ancestor`로 fast-forward 가능함을 먼저 확인한 뒤 `git checkout main` → `git merge --ff-only` → `git push`로 안전하게 복구. 데이터 유실은 없었지만, 지난 4개 세션이 `main`이 아닌 detached 상태에서 계속 작업해온 것으로 보여 **왜 세션이 매번 detached HEAD로 시작하는지** 원인 조사는 여전히 미해결 — 세션 종료/재시작 방식과 관련된 환경 이슈로 추정되나 다음 세션에서도 계속 관찰이 필요하다.
- LibreOffice headless 변환 문제가 5번째 세션째 동일하게 재현 확인됨(파일명 ASCII화, 격리된 프로필 지정까지 시도) — 근본 원인 조사는 계속 보류, 매번 손(Python) 계산 검증 경로로 바로 진행할 것. 이번엔 poppler-utils(`pdfinfo`/`pdftoppm`)도 설치돼 있지 않다는 점을 추가로 확인 — 페이지 수는 raw PDF의 `/Count` 값을 grep, 페이지별 스크린샷은 `screenshot_pdf_pages_cloud.js`(Chrome 내장 뷰어)로 대체하는 경로가 이 환경에서 안정적으로 동작함을 재확인.
- `scan_page_margins.py`의 정량 스캔이 이번엔 전 페이지 `bottom_empty_ratio=0.000`으로 나와 실질적인 신호를 못 줬다 — `screenshot_pdf_pages_cloud.js`의 뷰포트(850×1250)가 실제 PDF 페이지 높이와 정확히 맞아떨어지지 않아 페이지 경계마다 다음 페이지 상단 텍스트가 함께 캡처되며 "잉크가 항상 존재"로 오판된 것으로 추정. 정량 스캔이 이렇게 무의미해질 수 있으므로, Read 툴로 여러 페이지를 직접 육안 확인하는 절차는 스캔 결과와 무관하게 항상 병행할 것 — 이번에도 그렇게 진행해 실제로는 문제가 없음을 확인했다.
