# Day 27 — 2026-09-14

## 목표
로드맵.md에서 상태가 "대기"인 항목 중 Day 번호가 가장 작은 **Day 27 — AI로 블로그·애드센스 부수입 만드는 법 (전자책)**을 제작한다. Day01(전자책 디자인 정본)과 Day25(가장 최근 12방법+16프롬프트 구조 전자책)의 형식을 그대로 따르되, 2026년 시점의 애드센스 승인 기준 변화를 반영해 "AI로 글을 쓰되 승인·정책 리스크를 피하는 법"을 핵심 메시지로 잡는다.

### 3. 리서치(WebSearch) — 2026년 애드센스 승인·AI 콘텐츠 정책, 수익화 트렌드
- "티스토리 애드센스 승인 2026 AI 콘텐츠 정책" 검색 → 2026년 애드센스 심사가 예전보다 훨씬 까다로워졌고, "글 개수만 채우면 된다"는 접근이 더 이상 통하지 않으며, 심사가 글 개수·방문자 수보다 **사이트 전체의 원본 가치·탐색 구조·정책 준수**를 본다는 점 확인. "AI를 잘 쓰면 승인 준비가 쉬워질 수 있지만, AI에 전부 맡기면 오히려 멀어진다"는 논조를 다수 확인 → 이 책의 핵심 메시지(AI = 리서치·구조 설계 도구, 초안 검증은 사람 몫)로 그대로 채택.
- "구글 애드센스 AI 생성 콘텐츠 정책 2026 helpful content" 검색 → 구글이 콘텐츠 제작 방식(AI 여부)보다 실제 품질(E-E-A-T: 경험·전문성·권위성·신뢰성)을 기준으로 삼는다는 공식 입장을 재확인. AI 라벨링 요구는 광고 소재(이미지·영상)에 관한 것으로, 블로그 텍스트 콘텐츠 자체의 AI 사용을 금지하는 것이 아님을 확인 — 이 구분을 방법 9(AI 콘텐츠 정책 리스크 점검) 서술에 명확히 반영.
- "티스토리 워드프레스 비교 2026 블로그 수익화 쿠팡파트너스 애드센스 병행" 검색 → 수익화 성능은 워드프레스가 유리(광고 배치 자유도, 플러그인 확장성)하지만 티스토리는 무료+한국어 SEO 강점으로 여전히 접근성이 높다는 점, 네이버블로그는 애드센스 연동 자체가 불가능하다는 점, 제휴마케팅(쿠팡파트너스 등) 병행이 총수익을 끌어올리는 현실적 전략이라는 점을 확인 → 방법 1(플랫폼 비교표)과 방법 11(제휴마케팅 수익 다각화)에 반영.
- "애드센스 저품질 정책 위반 사이트 전체 무효화 2026 사례" 검색 → 2026년 구체 사례는 확보하지 못했으나, 정책 위반이 개별 페이지가 아니라 계정 전체 단위 조치로 이어질 수 있다는 공식 정책 문서 내용 확인 → 방법 10(광고 배치)의 "무효 클릭 시 계정 전체 정지" 경고 문구에 반영.
- **판단**: 검색 결과에서 "2026년 몇 월부터 정확히 어떤 기준이 바뀌었다"는 단일 공식 발표 원문은 확보하지 못했음(여러 블로그 운영자의 경험담 기반 정보가 대부분). 이에 따라 방법 5(승인 전략)에서 "글 개수보다 원본 가치·탐색 구조·정책 준수"라는 공통적으로 확인된 방향성만 서술하고, 특정 날짜나 수치를 단정하는 표현은 피함 — Day25의 "등록 직전 재확인 필수" 면책 패턴과 같은 접근.

### 4. 콘텐츠 설계 — 훅(제목)과 구조
- 제목을 Day25의 대구법 훅 패턴("사진은 있는데, 상세페이지가 없습니다")을 그대로 계승해 **"글은 쓰는데, 승인이 안 됩니다"**로 설계 — 리서치에서 확인한 "글 개수는 채웠는데 승인이 안 되는" 것이 2026년 애드센스 운영자들의 실제 공통 불만이라는 점과 정확히 맞아떨어짐.

### 6. PDF 렌더링 및 페이지 검증
- 이 세션에 `pdftoppm`(poppler-utils)이 설치돼 있지 않아 `apt-get install -y poppler-utils` 시도 → Day26 로그와 동일하게 `apt-get update` 없이 바로 설치하면 실패할 것으로 예상했으나, 이번엔 `apt-get update` 없이 바로 `apt-get install`을 실행해도 (PPA 저장소 2개의 403/서명 오류 경고만 뜨고) 핵심 패키지(`libpoppler134`, `poppler-utils`)는 정상 설치됨 — Day26과 달리 이번엔 1차 시도로 바로 성공. PPA 관련 경고는 poppler 설치와 무관한 별개 저장소 이슈라 무시.
- `scripts/render_pdf_cloud.js`로 렌더링 → **14페이지** 생성.
- **정량 여백 스캔 스크립트를 직접 작성하는 과정에서 버그를 발견하고 수정함**: 처음에는 "페이지 상단 20줄의 밝기를 배경(bg)으로 샘플링하고 그보다 12 이상 어두운 픽셀이 있는 마지막 행"을 콘텐츠 끝으로 판정하는 방식으로 작성했는데, 표지를 포함한 **14페이지 전부가 완전히 동일한 수치(`bottom_empty_ratio=0.060`)**로 나와 명백히 잘못된 결과임을 바로 알아챔.
  - **원인 분석**: `.page` 배경색(`--paper`, `#EEF0E8`)이 사실상 거의 흰색에 가까운 크림톤이고, PDF 렌더링 시 `@page` 여백(위아래 18mm)은 완전한 흰색(브라우저 기본 여백)으로 남는다. 상단 20줄을 "배경"으로 샘플링했을 때 이 완전한 흰색 여백 구간을 잡아버렸고, `thresh = bg - 12` 기준이 지나치게 민감해서 **본문 콘텐츠가 없는 빈 페이지 영역이라도 `--paper`색 자체가 흰 여백보다 살짝 어두워서 "콘텐츠 있음"으로 오판**됨. 즉 실제 텍스트/그래픽이 아니라 단순 배경색 채움 여부를 측정하고 있었던 것 — 모든 페이지가 `.page` 배경으로 끝까지 채워지니 모든 페이지가 같은 값으로 나온 것.
  - **수정**: 배경 대비 상대 임계값 대신, 실제 잉크(글자 `--ink` #262C3D, 골드 액센트 `--gold-strong` 등)만 잡히는 **절대 임계값(그레이스케일 210 미만)**으로 변경. 재실행 결과 표지(1p, 42.8%)·에필로그(14p, 51.2%)를 제외한 본문 12페이지가 9.1%~21.1% 범위로 나와 30% 기준을 모두 만족하는, 훨씬 신뢰할 수 있는 수치를 얻음.
  - **교훈(신규)**: 이런 디자인 시스템처럼 본문 배경색이 순백색이 아니라 옅은 톤(크림/페이퍼 톤)인 경우, "배경 대비 상대 임계값" 방식의 여백 스캔은 배경색 자체를 콘텐츠로 오인할 수 있다. 다음에 유사한 정량 스캔 스크립트를 짤 때는 처음부터 절대 밝기 임계값(잉크 색 기준)을 쓰거나, 최소한 결과값이 페이지마다 의심스러울 정도로 똑같이 나오면 로직 자체를 의심하고 실제 이미지를 먼저 육안으로 대조해야 한다.
- 수정된 스캔 결과를 신뢰한 뒤에도 Day26 로그의 교훈(정량 스캔은 "여백 과다"만 잡고 "라벨-콘텐츠 분리"는 못 잡는다)에 따라 `Read` 툴로 14페이지 전부를 순서대로 열어 육안 확인 — 목차, 표(방법1·방법11), worksheet-note 콜아웃, 프롬프트 A~D 카테고리 그리드(2단 배치, 색상 구분 정상), 체크리스트 3그룹, 에필로그까지 페이지 경계에서 라벨-콘텐츠 분리나 카드 잘림 없이 자연스럽게 이어지는 것을 확인. `.cat-label`을 `display:table`로 미리 설정해둔 덕분에 Day26에서 발생했던 분리 버그가 이번엔 재발하지 않음.

## 이슈/트러블슈팅
- **로컬 `main` 브랜치가 6일치(Day21~26) 뒤처진 채 detached HEAD 상태였음**: 세션 시작 시 `git fetch origin main` + `git checkout -B main origin/main`으로 즉시 원격 최신 상태로 맞춤. 원인은 특정되지 않았으나(이전 세션이 로컬 브랜치를 갱신하지 않고 종료됐을 가능성), 앞으로도 세션 시작 시 항상 `git fetch` + 로컬/원격 커밋 해시 비교를 먼저 할 것.
- **poppler-utils 설치가 Day26과 달리 `apt-get update` 없이 1차 시도로 성공**: PPA 저장소(`deadsnakes`, `ondrej/php`) 403 경고가 함께 떴지만 이 둘은 poppler와 무관한 별개 저장소라 설치 자체에는 영향 없었음. Day26 로그의 "update 먼저 실행" 교훈은 여전히 안전한 기본 순서지만, 이번 경우처럼 관련 없는 저장소 경고와 실제 설치 실패는 구분해서 판단해야 함.
- **정량 여백 스캔 스크립트의 "배경색 대 흰 여백" 오판 버그(신규 유형)**: 위 6번 항목에 상세 기록. 옅은 톤 배경(`--paper`)을 쓰는 디자인에서 상대 임계값 방식은 배경 자체를 콘텐츠로 오판할 수 있으므로, 앞으로는 처음부터 잉크 색 기준의 절대 임계값을 쓸 것. 이번엔 모든 페이지가 완전히 동일한 수치로 나온 것을 즉시 의심해서 발견·수정까지 마쳤지만, 다음부터는 스캔 스크립트를 새로 짤 때마다 결과값의 다양성(variance)을 먼저 확인하는 것을 표준 절차로 삼을 것.
- 2026년 애드센스 승인 기준 변경에 대한 "공식 발표 원문"은 WebSearch로 확보하지 못함(운영자 경험담 기반 정보가 대부분) — Day26의 법령 정보 면책 패턴과 동일하게, 특정 날짜·수치를 단정하지 않고 방향성 위주로 서술하는 방식으로 리스크 관리.
