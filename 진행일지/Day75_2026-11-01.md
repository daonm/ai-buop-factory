### 3. 주제 리서치 (WebSearch)
- "2026년 주택청약 가점제 무주택기간 부양가족수 청약통장 가입기간 산정기준" 검색 → 가점제는 무주택기간·부양가족수·청약통장 가입기간 3요소 합산 84점 만점이라는 점은 출처 간 일치. 가점제·추첨제 적용 비율은 출처마다 설명이 엇갈려(투기과열지구 75% vs 지역별 40% 등) 공고문 확인이 필요하다는 점을 확인.
- "청약 가점 계산법 만점 84점 당첨 전략 가점제 추첨제 비율 2026" 검색 → 배점 구성이 무주택기간 32점 + 부양가족수 35점 + 가입기간 17점 = 84점으로 출처 간 일치함을 재확인. 무주택기간은 만 30세·혼인신고일·주택 처분일 중 늦은 날부터 산정한다는 점, 동점 시 통장 가입기간이 긴 쪽이 우선한다는 점, 2026년 상반기 서울 주요 민영아파트 당첨선이 60점대에서 70점대로 올라갔다는 보도를 확인.
- "청약 가점제 무주택기간 1년미만 2점 15년이상 32점 표 부양가족 0명 5점 6명이상 35점 가입기간 6개월미만 1점 15년이상 17점" 검색 → 세 영역의 세부 배점 구간(무주택기간 1년마다 2점 증가/부양가족 1명당 5점 증가/가입기간 1년마다 1점 증가, 각각 15년·6명·15년에서 만점)이 여러 출처에서 일치함을 확인. 다만 미성년자 가입기간 인정 한도는 2024년에 개편된 적이 있다는 점도 확인해, 이 항목만 구체적 숫자를 고정하지 않고 "최신 공고로 재확인" 구조로 서술하기로 결정.
- 배점표 자체(84점 만점 구조, 3요소 구간별 증가 패턴)는 오랫동안 큰 틀이 유지돼 온 공개 정보라 판단해 표로 명시하되, 가점제·추첨제 적용 비율·특별공급 요건·규제지역 지정 현황처럼 공고·정책마다 바뀌는 항목은 Day73(연말정산)에서 세율 구간을 다룬 방식과 동일하게 구체적 수치를 고정하지 않고 "공고문·청약홈에서 재확인" 구조로 일관되게 서술.

### 4. 콘텐츠 구조 설계
Day73 패턴(기준값 확인 + 핵심 계산 단계 + 수익화 1챕터 + 실수 1챕터 + 시스템화 1챕터 + 프롬프트 15선 + 체크리스트, 총 16섹션·12가지 방법)을 그대로 따라 아래 순서로 설계:
1. 왜 지금 AI로 주택청약 가점·당첨 전략 계산 대행인가 / 2. 준비물 3가지 / 3. 방법1 무주택기간 점수 계산(32점) / 4. 방법2 부양가족수 점수 계산(35점) / 5. 방법3 청약통장 가입기간 점수 계산(17점) / 6. 방법4 총점 합산·당첨 커트라인 비교 / 7. 방법5 가점제·추첨제 적용 비율 확인 / 8. 방법6 가점 낮을 때 대체 전략 / 9. 방법7 특별공급 자격 매칭 / 10. 방법8 부부 통장 합산·중복청약 점검 / 11. 방법9 매년 바뀌는 제도 기준 확인 / 12. 방법10 대행 부업 수익화 / 13. 방법11 흔한 실수 6가지 / 14. 방법12 대행 시스템 구축 / 15. 프롬프트 15선(A.가점계산 B.전략수립 C.자격점검 D.대행서비스화, 각 4개씩) / 16. 실전 체크리스트(오늘/이번주/이번달 3단계)
- 이 주제만의 핵심 함정(무주택기간을 "나이−30"으로 단순 계산, 생활비 지원만으로 부양가족 포함, 통장 전환 시 가입기간 리셋 오해, 가점제 비율이 전 단지 동일하다는 오해, 세대원 중복청약, 가점 낮다고 바로 포기)을 13장 실수표에 명시적으로 반영.
- 기존 Day51~52(상속세·증여세)·Day71~72(해외주식 양도소득세)와 "세금 계산"이 아니라 "배점·전략 계산"이라는 점에서 다른 성격이지만, 역시 "당첨을 보장하지 않는 참고용 추정"이라는 톤은 동일하게 유지하고, 방법 10(수익화)에 "분양권 매매 중개, 공인중개사 업무, 당첨 보장 영업은 하지 않는다"는 경고 문구를 반영.

### 6. PDF 렌더링 및 검증
- `python3 -c "from PIL import Image"` 실행 시 `_imaging` 네이티브 확장 모듈이 깨져 있는 것을 재확인(Day63·65·67·69·71·73에서 반복된 것과 동일한 증상) → `python3 -m pip install --break-system-packages --force-reinstall --no-deps --ignore-installed pillow numpy`로 즉시 복구.
- `scripts/render_pdf_cloud.js`를 `PLAYWRIGHT_CHROMIUM_PATH=/opt/pw-browsers/chromium` 환경변수로 실행(Day73 인수인계 메모대로 바로 적용) — 이번 컨테이너는 `/opt/pw-browsers/chromium`과 `chromium-1243` 디렉터리가 모두 존재했고, 환경변수 오버라이드가 정상 동작함을 재확인.
- (1) `.cover` 673px 폭 검증 스크린샷, (2) 1000×1000·scale 2 썸네일, (3) A4(margin 18mm/16mm) PDF를 모두 생성.
- 생성된 PDF는 17페이지. `pdftoppm -png -r 150`으로 페이지별 PNG 변환 후 `scripts/scan_page_margins.py`(`-I` 플래그)로 하단 여백 비율을 정량 스캔.
  - 스캔 결과: 1페이지(표지) 38.6%만 30% 초과 — 설계상 의도된 독립 페이지라 정상. 17페이지(체크리스트→에필로그, 마지막 페이지)는 21.7%로 기준 이내. 나머지 15개 본문 페이지는 모두 7.2~14.7%로 과도한 빈 공간 없음(Day73과 거의 동일한 수치 분포).
- Read 툴로 PDF 페이지 PNG(4페이지: "시작 전에 3가지"→"무주택기간 점수 계산하기" 챕터 전환부, 15페이지: 프롬프트 15선 2단 그리드 A·B 카테고리, 17페이지: 체크리스트 3단계→에필로그)를 직접 육안 확인 — 카테고리별 색상 구분(골드/틸)·2단 그리드·원형 배지·챕터 전환이 의도대로 렌더링되고 끊김 없이 자연스럽게 이어짐.
- 673px 폭 캡처로 표지 문구("청약 넣기 전에", "AI한테 당첨 가능성부터 물어보세요", "12/15/3 + 단위") 모두 `nowrap` 처리되어 어색하게 끊기는 곳 없음을 확인.
- 1000×1000·scale 2 캡처를 `marketing/thumbnail.png`로 저장 — 별도 AI 이미지 생성 도구를 쓰지 않고 책 표지 디자인을 그대로 재사용.
- PDF 파일명은 `청약넣기전에_AI한테당첨가능성부터물어보세요.pdf`로 저장(Day67·69·71·73의 "~전에_AI한테먼저~.pdf" 네이밍 관례를 그대로 따름).
