### 2. 콘텐츠 설계 — FAQ 시나리오 스크립트
- 업종 5개 × FAQ 15개(영업정보/상품·서비스/결제·환불/기타 4개 카테고리로 세분)를 직접 작성. 단순 목록이 아니라 각 FAQ에 **카카오톡 대화창 3~4줄 기준 응답 스크립트**를 실제로 붙여넣을 수 있는 문장으로 작성하고, `[ ]`로 표시한 부분(가격·시간·정책)은 사용자가 반드시 실제 정보로 교체하도록 명시 — Day17 방법 4의 "가격·환불·영업시간처럼 틀리면 분쟁이 되는 정보는 AI가 임의로 지어내지 않는다"는 원칙을 그대로 계승.
- 업종마다 3단계 대화 흐름도(인사말 → 카테고리 버튼 → 이관)와 이관(핸드오프) 조건을 별도 박스로 정리. 특히 병원·전문 서비스 업종은 Day17 본문의 경고(챗봇이 증상 진단처럼 보이는 답변을 하면 법적 문제가 될 수 있음)를 그대로 반영해 "증상 관련 질문 전체는 예외 없이 즉시 이관"으로 명시.
- 산출물을 두 형태로 이원화: (1) `FAQ_스크립트_전체모음.md` — 업종별 15개 FAQ 전체를 markdown으로 복사하기 쉽게 정리 (2) `kit.html` — 업종별 대표 스크립트(6개씩, 총 30개)를 카테고리 색상·2단 그리드 레이아웃으로 시각화한 디자인 버전. 전체 75개를 모두 카드로 나열하면 PDF가 지나치게 길어질 것으로 판단해, kit.html은 "한눈에 훑어보는 대표 스크립트"로, 전체 75개는 markdown 파일에서 그대로 복사하는 역할 분담으로 구성.
- 워크시트(업종·채널 기본정보 / 이관 조건 정리 / 톤앤매너 체크)와 카카오톡 빌더 세팅 체크리스트(준비→등록→테스트→운영 4단계, 배지 스타일 재사용)를 markdown 파일과 kit.html 양쪽에 동일하게 반영.

### 3. 디자인 시스템 재사용 및 검증
- `kit.html`은 Day02/Day16과 동일한 CSS 변수(색상 토큰, 폰트: Gowun Batang + Noto Sans KR + Nanum Gothic Coding)와 클래스 관례(`.cat`~`.cat-e`, `.prompt-grid`, `.worksheet-num`, `.checklist-group h4 .wk` 등)를 그대로 재사용. 카테고리 5개(카페=gold, 쇼핑몰=terracotta, 학원=teal, 병원=olive, 미용실=plum)에 정확히 대응.
- **표지 문구 인쇄폭 검증**: 표지 h1 "AI 챗봇 FAQ 시나리오 스크립트 키트"를 뷰포트 673px(A4 PDF 실제 인쇄폭)로 캡처했더니 "시나리오"라는 단어가 "시나\n리오"로 어중간하게 쪼개지는 문제 발견. `<span class="nowrap">시나리오</span>`로 감싸 재캡처 후 정상 개행되는 것을 확인.
- **PDF 여백 검증**: `render_pdf_cloud.js`로 PDF 렌더링 후 총 8페이지 생성 확인. 처음에는 `screenshot_pdf_pages_cloud.js`(연속 스크롤 방식)로 페이지를 캡처했을 때 업종 카테고리 전환 지점에서 큰 빈 공간이 있는 것처럼 보여 문제로 의심했으나, 이 방식이 스크롤 중간 상태를 캡처해 실제 페이지 경계와 어긋난 이미지를 만드는 것으로 판명. 이를 확인하기 위해 Chrome 내장 PDF 뷰어의 `#page=N` 해시 네비게이션으로 각 페이지를 정확히 A4 픽셀 크기(794×1123px, 100% 줌)로 개별 캡처하는 임시 스크립트를 새로 작성해 8페이지 전체를 육안 검증 — 실제로는 모든 본문 페이지가 상단부터 하단까지 카드로 빼곡히 채워져 있고, 유의미한 빈 공간(30% 이상)은 없음을 확인. 워크시트 3(톤앤매너 체크)이 다음 페이지로 밀리며 생긴 약 19% 정도의 여백이 유일하게 눈에 띄는 지점이었으나 허용 범위로 판단.
- 최종 PDF(`챗봇_FAQ_시나리오_스크립트_키트.pdf`, 8페이지)와 썸네일(`marketing/thumbnail.png`, `.cover` 요소를 1000×1000 · deviceScaleFactor 2로 캡처)을 정식 산출물로 생성.

## 이슈/트러블슈팅
- **표지 문구 어중간한 개행**: 673px 인쇄폭 검증에서 "시나리오"가 "시나/리오"로 쪼개짐 → `nowrap` span으로 해결 (위 3번 참고).
- **PDF 페이지 캡처 방식 오판**: 기존 `screenshot_pdf_pages_cloud.js`(마우스클릭+PageDown 연속 스크롤 방식)로 캡처한 이미지에서 카테고리 전환부에 큰 빈 공간이 있는 것처럼 보여 실제 여백 문제로 오인할 뻔함. 원인은 스크롤 애니메이션 도중 캡처되어 두 페이지가 어긋나게 겹친 화면이 저장된 것 — 실제 페이지 경계와 무관한 착시였음. Chrome PDF 뷰어의 `#page=N` 해시로 페이지를 정확히 지정해 A4 실제 픽셀 크기로 재캡처한 뒤에야 실제로는 여백 문제가 없음을 확인. **다음부터 PDF 페이지별 여백을 검증할 때는 연속 스크롤 캡처보다 `#page=N` 해시 기반 개별 페이지 캡처가 더 신뢰도 높은 방법**이라는 것을 확인해, 정식 스크립트 `scripts/screenshot_pdf_page_exact_cloud.js`로 만들어 저장소에 추가함 (`node scripts/screenshot_pdf_page_exact_cloud.js <입력.pdf> <출력.png> <페이지번호>`).
- 그 외 특이 이슈 없음 — `NODE_PATH=/opt/node22/lib/node_modules` 지정, `/opt/pw-browsers`의 사전 설치 Chromium 사용 등 기존 클라우드 렌더링 파이프라인이 그대로 잘 작동함을 재확인.
